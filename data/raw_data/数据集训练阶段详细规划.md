# 电商多模态数据集训练阶段详细规划

## 1. 文档目的

本文档规定当前项目从原始商品数据到中文图文检索训练数据的处理顺序。当前不把不同来源的数据合并，先完成字段补全和数据一致性检查，再构建中文文本检索数据。

当前优先级只有两步：

1. 完成商品字段和图片关联的统一；
2. 基于统一后的字段生成中文图文检索样本。

分类训练、属性识别、描述生成和 Agent 工具调用放到检索基线稳定之后。

基本原则：

1. `data/raw_data/` 中的原始文件只读，不直接覆盖；
2. 每个数据集独立处理，不能因为字段名称相同就直接合并；
3. 所有项目内图片路径使用仓库根目录相对路径，并统一使用 `/`；
4. 缺失字段保留为空，不根据图片主观猜测品牌、颜色或材质；
5. 图片可读取只说明文件没有损坏，不代表图片内容一定与商品文字匹配；
6. 每个阶段都要保存输入、输出和检查结果，便于重复处理。

## 3. 正式商品表字段

正式处理后的 `products.csv` 固定使用以下 11 个字段：

```text
item_id
product_type
item_name
description
brand
color
material
local_image_path
image_status
image_height
image_width
```

字段规则：

| 字段 | 规则 |
|---|---|
| `item_id` | 数据集内唯一的商品 ID；不同数据集不要求全局合并 |
| `product_type` | 使用大类，如 `包`、`鞋`、`水杯`，不写过细品类 |
| `item_name` | 清理后的商品标题或名称，保留来源文本的主要信息 |
| `description` | 商品补充描述；当前 MUGE 暂时为空，不从图片猜测 |
| `brand` | 仅保留来源中明确给出的品牌，未知时为空 |
| `color` | 仅保留来源中明确给出的颜色，未知时为空 |
| `material` | 仅保留来源中明确给出的材质，未知时为空 |
| `local_image_path` | 相对于仓库根目录的图片路径 |
| `image_status` | 当前图片状态，如 `ok`、`missing`、`failed` |
| `image_height` | 实际读取到的图片高度 |
| `image_width` | 实际读取到的图片宽度 |

`source_image_id` 和 `source_image_path` 不属于正式商品表字段。来源说明、许可证和原始文件名放在数据集 README 或版本清单中，不放入商品主表。

`image_quality_report.csv` 只记录图片技术检查结果，例如是否能解码、实际尺寸、格式、文件大小、哈希和检查状态，不重复商品描述字段。

## 4. 当前处理阶段和顺序

```text
M0  冻结原始数据和字段契约
 ↓
M1  补全字段、统一类别和路径
 ↓
M2  图片路径及技术质量检查
 ↓
M3  生成中文图文检索数据
 ↓
M4  运行中文文本检索基线
 ↓
M5  根据误差结果再做内容审核、属性标签和其他任务
```

### M0：冻结原始数据和字段契约

目标：确定输入版本和统一字段，不修改原始目录。

检查内容：

1. 记录数据集名称、来源、日期和许可说明；
2. 确认商品 CSV、图片目录和质量报告属于同一版本；
3. 确认每条商品记录的图片路径可解析；
4. 确认正式表使用 11 个字段；
5. 确认缺失值使用空字符串，不把缺失当成否定标签。

### M1：补全字段、统一类别和路径（当前第一优先级）

这一步不是生成模型训练，而是把不同来源的数据整理成可检查的统一商品表。

处理规则：

1. 根据数据集原字段建立映射，不同来源分别配置；
2. `product_type` 统一为大类，MUGE 使用 `双肩包=包`、`运动鞋=鞋`；
3. `item_name` 清理空格、编码和明显的多余符号；
4. `description` 当前 MUGE 保持为空，后续是否生成描述另行决定；
5. `brand`、`color`、`material` 只复制来源中可靠的值，不能从图片推断；
6. 统一图片路径为相对路径；
7. 读取图片实际尺寸，写入 `image_height` 和 `image_width`；
8. 生成统一字段的 `products.csv`。

M1 验收标准：

- 11 个字段名称和顺序固定；
- 数据集内 `item_id` 不重复；
- `product_type` 只使用约定的大类；
- 所有非空图片路径都能定位到文件；
- 原始 CSV 没有被覆盖；
- 缺失的品牌、颜色、材质和描述保持为空，而不是被猜测填充。

### M2：图片路径及技术质量检查

这一阶段只做可自动验证的检查：

- 文件是否存在、大小是否大于 0；
- 图片是否可以解码；
- CSV 声明的尺寸和实际尺寸是否一致；
- 图片格式、文件大小和 SHA-256；
- `image_status` 是否与实际文件状态一致；
- 商品 ID 是否重复、图片路径是否为绝对路径。

当前使用的输出文件仍然是：

```text
products.csv
images/
image_quality_report.csv
field_check_report.json
```

图片是否真的展示对应商品、是否清晰、是否与标题语义匹配，属于后续内容审核，不在这一步假定为已完成。

### M3：生成中文图文检索数据

只有 M1 和 M2 通过后才开始这一步。

首轮文本使用：

1. `item_name`；
2. 如果后续补充了可靠的 `description`，再将其拼接到检索文本；
3. 空的品牌、颜色和材质不强行补入文本。

建议的单条样本结构：

```json
{
  "item_id": "muge_741",
  "image_path": "data/processed_data/水杯/images/741.jpg",
  "text": "网红冬天的第一杯奶茶",
  "product_type": "水杯"
}
```

训练集、验证集和测试集按 `item_id` 划分，不能让同一商品的图片或文本同时出现在不同划分中。检索数据属于训练资源，应放在后续实验输出目录，不回写原始数据。

### M4：中文文本检索基线

M3 的数据准备完成后，先使用预训练视觉语言模型做冻结编码器或小规模基线，再考虑微调。此阶段才处理模型、配置、日志、指标和误差分析。

### M5：后续任务

以下内容不属于当前第一轮工作：

- 图片主体和文字语义的人工审核；
- 近似图片去重和错配样本清单；
- 颜色、材质、风格等属性人工标注；
- 商品描述生成；
- 分类模型和 Agent 工具调用训练。

这些任务应在中文文本检索基线完成后，根据误差分析决定是否开展。

## 5. 各数据集的字段处理边界

### 5.1 MUGE

MUGE 是当前首个处理对象。它已有中文商品标题和三类来源类别：

```text
双肩包 → 包
运动鞋 → 鞋
水杯   → 水杯
```

品牌、颜色、材质当前为空时继续保留为空。`description` 按当前决定暂时为空。

### 5.2 Amazon

Amazon 原始表中的标题、类别、品牌、颜色和材质分别映射到统一字段。英文标题翻译属于独立的暂存步骤，不能覆盖原始数据，也不能在未完成字段映射前直接进入检索训练。

### 5.3 Suning

Suning 的 `products.csv` 除统一商品字段外还包含价格、来源链接和采集日期。首版统一表只保留 11 个正式字段，其余信息作为来源数据说明或后续扩展字段保存，不与 MUGE 合并。

### 5.4 GoodsCls

GoodsCls 使用 `id`、`title`、`description`、`categories` 等字段，且训练集和测试集的标签结构不同。需要先建立独立字段映射和图片路径规则，不能直接套用 MUGE 的脚本和类别映射。

## 6. 当前脚本与文档的对应关系

| 脚本 | 当前作用 |
|---|---|
| `scripts/classify_products.py` | 读取已有 `product_type`，按类别整理商品记录、复制图片并生成技术质量报告 |
| `scripts/check_product_fields.py` | 检查字段、重复 ID、图片路径和 `image_status` |
| 中文检索脚本 | 当前尚未编写，等 M1、M2 完成后再设计 |

当前 `classify_products.py` 是数据整理器，不是根据图片预测类别的机器学习分类模型。

现有历史输出的 `image_quality_report.csv` 中可能仍有 `source_image_path` 列；该列不属于最终字段契约，后续清理报告格式时删除。正式方案不使用 `source_image_id`。

# 电商多模态数据集训练阶段详细规划

## 1. 文档目的

本规划用于指导商品图片、商品文本和商品元数据采集完成后的下一阶段工作。目标是把当前数据整理为可复现、可审核、可训练、可评估的多模态数据集，并先完成一个商品图文检索基线，再逐步扩展到商品分类、属性识别、文案生成和 Agent 工具调用。

本规划遵循以下原则：

1. 原始数据只读保存，不在 `data/raw_data/` 中直接覆盖或修正。
2. 所有数据路径使用仓库根目录相对路径，并统一使用 `/` 作为分隔符。
3. 图片可读取不等于图片是合格的商品图，图片内容需要单独审核。
4. 缺失属性表示没有可靠标注，不把缺失值当成否定标签，也不根据图片主观补写。
5. 每个训练样本都能追溯到数据集来源、原始记录、图片文件和审核结果。
6. 先完成数据质量闭环和小规模基线，再扩大训练规模或增加任务。

### 2.3 首轮训练任务选择

首轮任务确定为：

> 商品图片—中文文本检索。

选择该任务的原因是 MUGE 原始数据具有商品图片和中文检索文本，能够在不补齐颜色、材质等属性的情况下形成监督信号。首轮不从零训练大模型，而是使用预训练视觉语言模型进行微调或先做冻结编码器基线。

以下任务放到后续阶段：

- 颜色、材质、风格等属性识别：需要可靠的人工或来源标签；
- 商品标题和描述生成：需要经过审核的目标文案；
- Agent 工具调用：需要用户需求、工具调用、工具结果和最终回答组成的轨迹数据。

## 4. M0：数据版本和数据契约冻结

### 4.1 任务

1. 记录当前 Git 提交号、数据集来源、采集或整理日期和许可信息。
2. 对两个数据集的 CSV、图片目录和质量报告做数量核对。
3. 确认每条商品记录都能定位到一张图片。
4. 确认 `products.csv` 和 `image_quality_report.csv` 中使用的是相对路径。
5. 为每个数据集保留原始说明和许可说明。

### 4.2 统一数据字段

处理后的主表建议统一为：

```text
product_id

description
category_lv1
category_lv2

color
material
style
usage_scene
feature_tags
price
stock_status
source

image_role
product_visible

review_reason
```

新增的审核字段不覆盖原始字段，原始来源字段保留在 `source_*` 字段或来源清单中。

### 4.3 缺失值约定

- 单值字段缺失使用空字符串 `""`；
- 多值字段统一使用 JSON 空数组 `[]`；
- 不使用混合的 `null`、`NaN`、`unknown`、`[]` 表示同一种含义；
- `unknown` 只在字段确实经过检查但无法确定时使用；
- 不根据图片或标题猜测品牌、颜色、材质。

### 4.4 M0 验收标准

- 原始目录没有被脚本覆盖；
- 记录数、图片数、报告数可相互核对；
- 不存在绝对路径；
- 所有图片路径可以定位到文件；
- 每条处理后数据可以追溯到 `source` 和 `license`。

## 5. M1：图片内容审核、去重和匹配检查

### 5.1 新增审核表

建议新增：

```text
data/processed_data/image_audit.csv
```

字段如下：

```text
source
product_id
image_id
image_path
image_role
product_visible
match_status
review_status
review_reason
reviewer
review_date
```

### 5.2 字段取值

`image_role`：

```text
product_main       商品主体清楚的主图
product_context    商品在场景中可辨认
non_product        非商品图片或与商品无关
uncertain           无法确定
```

`product_visible`：

```text
true
false
unknown
```

`match_status`：

```text
matched
mismatched
unknown
```

`review_status`：

```text
approved
rejected
pending
```

### 5.3 审核规则

可以进入商品正样本的图片必须满足：

```text
product_visible=true
match_status=matched
review_status=approved
```

以下图片从商品正样本中排除或单独保留：

- 没有商品主体的风景、人物、纯文字或装饰图片；
- 商品太小、严重遮挡或无法确认商品类别；
- 多商品拼图但无法确定对应商品；
- 图片内容与标题、类别或商品 ID 不匹配；
- 仅有包装、配件或局部细节，且训练任务需要完整商品主体；
- 重复图片或同一商品的错误关联图片。

非商品图片不要直接删除。保留并标注为 `non_product`，后续可用于拒识测试和异常检测。

### 5.4 去重和一致性检查

同时做以下检查：

1. 使用 SHA-256 检查完全重复文件；
2. 使用感知哈希或人工抽样检查近似重复图片；
3. 检查一张图片是否被多个不同商品 ID 复用；
4. 检查文本是否与图片 ID 一致；
5. 检查质量报告中的尺寸和实际图片尺寸是否一致；
6. 记录所有被排除样本的原因，不静默删除。

### 5.5 M1 交付物和验收

交付物：

```text
data/processed_data/image_audit.csv
data/processed_data/dedup_report.csv
data/processed_data/content_review_summary.json
```

验收要求：

- 每张参与训练的图片都有审核状态；
- 非商品图片不会进入商品正样本；
- 近重复图片不会跨训练集、验证集和测试集；
- 审核统计包含通过、拒绝和待复核数量；
- 抽查结果与审核字段一致。

## 6. M2：元数据和类别标准化

### 6.1 统一三类目标类别

首轮可以使用以下目标类别：

```text
双肩包
运动鞋
水杯
```

MUGE 类别可以直接映射。ABO 的原始 `product_type` 和类目路径需要建立显式映射表，不要仅根据关键词强行映射。

建议新增：

```text
data/processed_data/category_mapping.csv
```

字段：

```text
source
source_category
target_category
mapping_status
mapping_reason
review_status
```

无法可靠映射的记录标记为 `unmapped`，可以保留在原始数据中，但不能进入三分类训练集。

### 6.2 处理 ABO 的已知风险

ABO 当前数据中存在宽泛类目和规则筛选误差风险。特别是 `HOME`、`KITCHEN` 等宽类目不能直接作为水杯或其他细分类别。应根据标题、原始类目路径和图片共同抽查，必要时标记为 `uncertain`。

### 6.3 处理 MUGE 的缺失属性

MUGE 的 `brand`、`color` 和 `material` 为空时保留为空。后续如果需要属性训练，应新增单独的人工标注表：

```text
data/processed_data/attribute_labels.csv
```

建议字段：

```text
product_id
image_path
attribute_name
attribute_value
evidence_type
confidence
annotator
review_status
```

属性值必须注明来源：`metadata`、`image`、`text` 或 `human_review`。无法确认的属性不做正标签。

### 6.4 M2 验收标准

- 目标类别值来自固定词表；
- 原始类别和目标类别的映射可追溯；
- 未映射或待复核样本不进入首轮分类训练；
- 属性空值没有被误转成负标签；
- 主表中的路径、来源和许可字段完整。

## 7. M3：训练集、验证集和测试集构建

### 7.1 推荐目录

```text
data/processed_data/
├── products.csv
├── image_audit.csv
├── category_mapping.csv
├── source_manifest.csv
├── retrieval/
│   ├── train.jsonl
│   ├── val.jsonl
│   └── test.jsonl
├── classification/
│   ├── train.csv
│   ├── val.csv
│   └── test.csv
└── reports/
    ├── dataset_summary.json
    ├── split_summary.json
    └── excluded_samples.csv
```

### 7.2 图文检索样本格式

每行一个 JSON 对象：

```json
{
  "image_id": "670822",
  "image_path": "data/raw_data/MUGE_data/images/670822.jpg",
  "text": "鞋子黑色蓝色男运动鞋",
  "category": "运动鞋",
  "product_id": "muge_670822",
  "source": "MUGE"
}
```

当前仓库的 `MUGE_data` 原始目录只有商品主表和图片。如果使用原 MUGE 的多文本图文对，需要把对应的 `image_text_pairs.jsonl`、`train.csv`、`val.csv` 作为处理后训练资源复制到 `data/processed_data/retrieval/`，并重新写成统一相对路径。原始 MUGE 文件不能直接假定为当前仓库已经存在。

### 7.3 划分规则

建议初始比例：

```text
训练集：80%
验证集：10%
测试集：10%
```

划分单位应为 `product_id` 或 `image_id`，而不是文本行。一个商品的多条文本必须进入同一划分，不能让同一图片的一条文本进入训练集、另一条文本进入测试集。

### 7.4 负样本

首轮保留两类负样本：

1. 同类别不同商品：用于区分相似商品；
2. 非商品或错配图片：用于拒识和错误匹配评估。

负样本必须记录生成方式，不把未经确认的错配样本当作普通负样本。

### 7.5 数据统计

每次生成数据集都输出：

- 各数据集记录数和图片数；
- 各类别数量；
- 训练、验证、测试数量；
- 文本长度分布；
- 图片尺寸分布；
- 缺失字段统计；
- 重复和排除样本数量；
- 每个来源在各划分中的数量。

## 8. M4：首轮图文检索基线

### 8.1 训练路线

按以下顺序进行：

1. 使用预训练 Chinese-CLIP 直接提取图片和文本向量；
2. 建立不微调的零样本或冻结编码器检索基线；
3. 使用 MUGE 训练集进行图文对比学习微调；
4. 在 MUGE 测试集上评估；
5. 使用 ABO 作为跨来源测试集，观察域差异；
6. 比较微调前后的检索效果。

不要在第一轮直接训练一个新的大模型，也不要在只有空属性字段的情况下做属性监督微调。

### 8.2 初始训练配置

初始配置建议记录在：

```text
configs/retrieval/muge_baseline.yaml
```

至少记录：

```text
base_model
image_size
max_text_length
batch_size
learning_rate
epochs
random_seed
train_manifest
val_manifest
test_manifest
```

显存不足时优先使用梯度累积、混合精度或冻结部分编码器，并在配置中记录实际设置。

### 8.3 训练产物

```text
runs/retrieval/<run_id>/
├── config.yaml
├── checkpoint/
├── train_log.jsonl
├── metrics.json
├── predictions.jsonl
└── data_manifest.json
```

`data_manifest.json` 必须记录数据文件的相对路径、行数、Git 提交号和文件哈希，保证以后可以复现实验。

### 8.4 首轮指标

至少记录：

- Image-to-Text Recall@1、Recall@5、Recall@10；
- Text-to-Image Recall@1、Recall@5、Recall@10；
- MRR；
- 按商品类别分别统计的指标；
- 过滤非商品图前后的指标；
- MUGE 内部测试和 ABO 跨来源测试结果。

## 9. M5：评估和误差分析

### 9.1 必做检查

1. 抽取检索结果排名靠前但实际错配的样本；
2. 检查模型是否只依赖背景、颜色或文字水印；
3. 检查三类商品中是否有一类明显占优；
4. 检查非商品图片是否被错误匹配到商品；
5. 检查跨来源测试是否显著下降；
6. 区分数据错误、标签错误、模型错误和任务定义错误。

### 9.2 误差分类

建议把错误分为：

```text
label_error
image_text_mismatch
duplicate_leakage
non_product_image
category_confusion
attribute_confusion
model_ranking_error
```

每类错误至少保存若干样本、图片路径、文本、预测结果和修复建议。

### 9.3 继续训练的判断

- 若主要错误是错配或非商品图：先修数据，不调模型；
- 若主要错误是类别映射问题：先修类别表并重新划分；
- 若训练集好、测试集差：检查重复、泄漏和来源偏差；
- 若 MUGE 内部和跨来源都较差：先检查文本对格式、路径和训练配置；
- 只有数据质量稳定后，才增加模型规模或训练轮数。

## 10. M6：扩展分类和属性识别

### 10.1 商品类别分类

在检索基线稳定后，使用经过审核的 `category_lv1` 做分类：

1. 先冻结视觉编码器训练线性分类器；
2. 再比较小范围视觉编码器微调；
3. 使用分层划分，保证三类在训练、验证和测试中都有样本；
4. 报告 Macro-F1、各类别 Precision、Recall、F1 和混淆矩阵。

### 10.2 属性识别

只使用 `attribute_labels.csv` 中审核通过的属性标签。颜色、材质和风格应分别建任务或明确多标签任务，不把多个属性拼成无法解析的字符串。

每个属性标签至少记录：

- 标签来源；
- 标注人或标注规则；
- 是否二次审核；
- 置信度；
- 允许的词表值。

### 10.3 生成任务

标题和描述生成需要新增人工审核目标：

```json
{
  "image_path": "data/raw_data/MUGE_data/images/741.jpg",
  "verified_attributes": {
    "category": "水杯",
    "color": "白色"
  },
  "instruction": "生成30字以内商品标题",
  "target": "简约白色马克杯"
}
```

生成目标必须来自商品事实，不能让模型根据无法确认的图片细节虚构材质、功能或品牌。

## 11. M7：构造 Agent 对话和工具调用数据

在检索和属性识别可用后，再生成 Agent 训练样本。

### 11.1 工具调用样本结构

```json
{
  "id": "dlg_000001",
  "messages": [
    {"role": "user", "content": "找一双黑色运动鞋"},
    {
      "role": "assistant",
      "tool_call": {
        "name": "search_products",
        "arguments": {"category": "运动鞋", "color": "黑色", "top_k": 5}
      }
    },
    {
      "role": "tool",
      "name": "search_products",
      "content": "[{\"product_id\":\"...\"}]"
    },
    {"role": "assistant", "content": "为你找到相关运动鞋。"}
  ]
}
```

### 11.2 必须覆盖的样本

- 正常商品检索；
- 图片分析后检索；
- 缺少颜色或材质时的澄清；
- 没有匹配商品时的明确反馈；
- 工具参数错误后的修正；
- 非商品图片的拒识；
- 商品属性冲突时不编造结论。

工具调用数据应经过人工抽查，不能只用模板批量生成后直接训练。

## 13. 建议执行顺序

### 第一轮：数据审核

1. 建立 `image_audit.csv`；
2. 审核非商品图、错配图和不清晰图；
3. 做重复图片和孤立文件检查；
4. 输出排除样本清单。

### 第二轮：训练数据构建

1. 复制或整理 MUGE 图文对到处理后目录；
2. 统一 JSONL 字段和相对路径；
3. 按商品或图片分组划分 train、val、test；
4. 输出数据统计和哈希清单；
5. 对文本、图片和类别随机抽样复核。

### 第三轮：检索基线

1. 运行预训练模型基线；
2. 运行 MUGE 微调；
3. 计算检索指标；
4. 保存配置、日志、模型和预测结果；
5. 完成误差分析。

### 第四轮：标签补充

1. 根据误差分析决定优先补充的属性；
2. 建立颜色、材质和风格词表；
3. 人工标注并二次审核；
4. 建立分类和属性识别数据集；
5. 再训练分类或属性模型。

### 第五轮：Agent 任务

1. 固定检索和图片分析工具接口；
2. 构造并审核工具调用轨迹；
3. 加入错误恢复和拒识样本；
4. 做 LoRA 或其他参数高效微调；
5. 进行端到端多轮评估。

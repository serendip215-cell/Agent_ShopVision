## 一、为什么选量化（六个任务对比）

| 任务 | 适配度 | 理由 |
|---|---|---|
| **3.1.1 量化** | ⭐ **选它** | 实验二的权重、双塔、固定验证集、评测脚本全现成；任务书要的「CV 塔静态量化 + NLP 塔动态量化」正好对应我们的图像塔 + 文本塔 |
| 3.1.2 剪枝 | 次选（降为可选加分） | 要 L1 通道剪枝 + 注意力头剪枝 + 剪后微调 3–5 轮，相当于再训一次，是六个里第二重的活 |
| 3.1.3 蒸馏 | 不做 | 需要一个更大的同构教师模型（我们没有），还要训 10–15 epoch，直接排除 |
| 3.1.4 推理加速 | 顺带做 | 不改参数量，填不了报告第 2 条的「压缩前后对比表」；但 ONNX 导出是量化权重的另存格式，成本极低 |
| 3.1.5 资源占用 | 不做 | 稀疏存储 + 内存复用 + 动态加载，工程量大、与检索链路耦合差、收益说不清 |
| 3.1.6 鲁棒性 | 不做 | PGD 对抗训练 + 微调 5 epoch，要重训，且偏离「轻量化」主题 |

选量化的四条硬理由：

1. **指标口径天然对齐**：任务书要 Top-1 准确率损失，我们的 **R@1 就是 Top-1 命中率**，ΔR@1 直接当 ΔAccuracy，不用造新指标。
2. **目标数字轻松达标**：模型约 188M 参数，**纯 FP32 权重约 718MB / FP16 约 359MB / INT8 约 188MB**。任务书那句「体积减少 75%」对应的是 **FP32→INT8**（750→188）；FP16→INT8 只有 −50%，写报告时别混。剪枝要凑 FLOPs −30% 得反复扫比例。
3. **报告第 2 条它全包**：参数量、模型大小（文件字节）、精度损失、**误差分布热力图**（9 类别 × 各精度组的 ΔR@1，分类别汇总现成）。
4. **退路最多、最省学时**：FP16 基线零成本，INT8 是 PyTorch 内置，4-bit 装不上就退回两组照样达标；剪枝/蒸馏要重训，出问题就卡死。

### 1.1 任务书原文要求 vs 我们的实现（🧊 已冻结，留档）

> **状态：3.1.1 量化已冻结（2026-10-23）**。本节保留完整的"要求—实现—实测—返工计划"记录，
> 供报告引用；**不再继续做量化实验**，主任务切换到 3.1.4 推理加速（见开头「任务切换」与
> [`docs/optimize/02-推理加速（3.1.4）.md`](../optimize/02-推理加速（3.1.4）.md)）。

**原文出处**：`docs/课程材料/实验3任务书.pdf` 第四节「任务 3.1.1 模型量化实现」。

#### 原文怎么写的

> 1. 量化方法选择：
> - 针对实验 2 的 **ResNet-18（CV 模型）**：采用**静态量化**（需校准数据）；
> - 针对实验 2 的 **DistilBERT（NLP 模型）**：采用**动态量化**（适合文本推理）。
> - 【**选做/拓展**】若实验 2 选用 **Transformer 类**或小型语言模型，可选做以下一种量化对比：
>   GPTQ（W4A16）、AWQ、SmoothQuant（W8A8）、旋转量化（QuaRot/DuQuant）或 KV Cache INT8 量化。
>   选做只需报告困惑度或分类准确率变化，**不要求实现 QAT，不要求 FP4**。
>
> 3. 量化效果评估：
> - 参数量对比：计算量化前后模型大小（**如** FP32→INT8，模型体积减少 75%）；
> - 精度对比：用实验 1 的测试集评估 Top-1 准确率损失（**目标 ≤2%**）。

难点突破部分还写了两条补救手段：

> - 校准优化：增加校准数据量（实验 1 训练集前 500 样本），或采用**混合精度量化（权重 INT8 + 激活 FP16）**；
> - 微调恢复：对量化/剪枝后的模型用实验 1 的训练集小批量**微调（1-3 个 epoch）**，恢复精度损失。

#### 四条必须纠正的认知

| # | 原文 | 我们之前的做法 | 结论 |
|---|---|---|---|
| 1 | 必需部分针对 **ResNet-18 / DistilBERT** | 直接套用"CV 塔静态 + NLP 塔动态" | 我们的实验二是 ViT+RoBERTa，属【选做】说的"Transformer 类"；映射到我们的两塔合理，但报告要说明依据 |
| 2 | −75% 是"**如** FP32→INT8"的**举例** | 当成硬指标，纠结达不到 | **不是验收指标**；硬指标是精度 ≤2% |
| 3 | 明确提出**混合精度（权重 INT8 + 激活 FP16）** | 只做纯 INT8 直接推理 | 未采用，是精度崩掉的重要可避免因素 |
| 4 | 明确提出**量化后微调 1–3 epoch 恢复** | 没做 | 未采用，白白放弃了恢复精度的合法手段 |

#### 我们的实测（纯动态 INT8，无校准、无混合精度、无微调）

934 条 test，R@1，详见 [`docs/optimize/runs/2026-10-23_exp3-quant/02-精度评测.md`](../optimize/runs/2026-10-23_exp3-quant/02-精度评测.md)：

| 配置 | 体积 | R@1 | ΔR@1 |
|---|---:|---:|---:|
| FP32 | 718 MB | 58.57 | +0.11 |
| FP16（官方默认） | 359 MB | 58.46 | 基准 |
| INT8 动态 · per-tensor | 314 MB | 6.64 | −51.82 |
| INT8 动态 · per-channel | ~314 MB | 25.05 | −33.41 |
| INT8 动态 · 只文本塔 | ~463 MB | 8.89 | −49.57 |
| INT8 动态 · 只图像塔 | ~548 MB | 45.40 | −13.06 |

**结论**：纯动态量化（无校准、无混合精度、无微调）不可行。但原文给的两条补救我们尚未使用，不能据此判定"量化不可行"。

#### 返工计划（P2′，按原文要求）

1. **图像塔**：ONNX 静态量化（QDQ）— 权重 per-channel，激活用**训练集前 500 条**校准；
2. **文本塔**：动态量化（原文推荐）；若仍崩，则保 FP16 并在报告写明取舍；
3. **混合精度**：权重 INT8 + 激活 FP16（原文"难点突破"推荐），作为精度不达标时的第二方案；
4. **微调恢复**：量化后小批量微调 1–3 epoch（沿用实验二配方，lr 减半）；
5. 评测：同一 934 条 test 的 R@1，目标 **≤2pp**；
6. 体积：如实报实测值，不再以 −75% 为硬性目标（原文是举例）。

**载体为什么是 ONNX**：PyTorch 静态量化不支持 ViT 的 LayerNorm/GELU（第九节风险表第一行），ONNX Runtime 的 QDQ 能覆盖 Conv/MatMul/Gemm。此时 ONNX 不再只是"另存格式"，而是**静态量化的必要载体**。

## 二、任务书 → 本项目的映射（别照抄任务书）

任务书是按「ResNet-18（分类）+ DistilBERT（分类）」写的通用指导；我们实验二是 **Chinese-CLIP ViT-B/16 中文图文检索**：

| 任务书写法 | 我们的对应 | 说明 |
|---|---|---|
| ResNet-18（CV 模型） | **图像编码器 ViT-B/16** | 双塔的视觉那一路 |
| DistilBERT（NLP 模型） | **文本编码器 RoBERTa-wwm-ext-base-chinese** | 双塔的文本那一路；模型共约 188M 参数 |
| Top-1 准确率 | **Recall@1** | R@1 即 Top-1 命中率，R@5 对应 Top-5 |
| `./data/dataset/test.csv` | 实验一 8:1:1 划分出的 **test 934 条**（来自清洗数据 9,393 条） | 另加端到端口径：固定 132 查询 / 1325 标签 |
| 校准数据（训练集子集） | 实验一训练集前 500 条 | **必需**：静态量化（ONNX QDQ）靠它统计激活范围 |
| FLOPs 减少 30%（剪枝目标） | 量化**不改 FLOPs 计数**，改位宽与带宽 | 表里同时给「FLOPs」和「等效位宽 / bit-ops」，别混为一谈 |
| ResNet 的残差结构 | ViT-B/16 的残差连接 + LayerNorm + 多头注意力 | 报告第 4 条的关联分析按 ViT 写 |

**精度口径统一**：所有「ΔAccuracy」一律写成 **ΔR@1（百分点）**；两组测试口径都跑：模型级 934 条、端到端 132 查询。

容器 `shopvision`，仓库在容器内 `/workspace`。命令从 WSL 宿主机发起；`.sh` 脚本要 `tr -d '\r'` 清 Windows 换行符（见 `scripts/finetune/README.md`）。

### 5.1 P0 环境（已按实际执行改写，2026-10-25）

**依赖版本必须锁死**，否则会踩 CUDA 版本坑：

| 包 | 必须装 | 说明 |
|---|---|---|
| torch | 2.7.1+cu128 | 镜像自带 |
| onnx | 1.23.2 | 导出 + 图层面转 fp16 |
| **onnxruntime-gpu** | **1.22.0** | ⚠️ **不要装 `>=1.20`**：会拉到 1.31，它要求 **CUDA 13**，加载 `libcublasLt.so.13` 失败并**静默回退 CPU** |
| **tensorrt** | **10.x（cu12）** | ⚠️ 直接 `pip install tensorrt` 会给 11.x（cu13），而 ORT 1.22 链接的是 `libnvinfer.so.10`，同样失败回退 |

```bash
pip install "onnxruntime-gpu==1.22.0"

# TensorRT 必须是 10.x：先卸 11，再装 cu12 的 10.x（国内源 + 绕代理）
pip uninstall -y tensorrt tensorrt-cu13 tensorrt-cu13-bindings tensorrt-cu13-libs
env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy \
  pip install "tensorrt-cu12>=10,<11" -i https://mirrors.aliyun.com/pypi/simple \
  --trusted-host mirrors.aliyun.com --timeout 600
```

**每个新 shell 必做**（否则 ORT/TRT 找不到 cuDNN 与 TensorRT 库）：

```bash
export LD_LIBRARY_PATH=$(python -c "
import glob, os
d = []
try:
    import tensorrt_libs; d.append(os.path.dirname(tensorrt_libs.__file__))
except ImportError: pass
d += ['/usr/local/cuda/lib64', '/usr/lib/x86_64-linux-gnu', '/opt/conda/lib']
d += sorted(glob.glob('/opt/conda/lib/python3.11/site-packages/nvidia/*/lib'))
print(':'.join(x for x in d if os.path.isdir(x)))
")
```

**本机实测（2026-10-25，容器内）**：torch 2.7.1+cu128 / onnx 1.23.2 / **onnxruntime-gpu 1.22.0** /
**TensorRT 10.x**；`get_available_providers()` = `['TensorrtExecutionProvider', 'CUDAExecutionProvider', 'CPUExecutionProvider']`。

> 延迟对比必须**同硬件**：`PyTorch-CPU vs ORT-CPU`、`PyTorch-GPU vs ORT-GPU/TRT`。跨硬件比出来的加速比不可用。

  --provider CUDAExecutionProvider --batch 1 32

### 5.4 常见失败与处理（都是实际踩过的）

| 现象 | 原因 | 处理 |
|---|---|---|
| `Failed to load libonnxruntime_providers_cuda.so: libcublasLt.so.13` | onnxruntime-gpu 1.31 要 CUDA 13 | 装 `onnxruntime-gpu==1.22.0` |
| `libnvinfer.so.10: cannot open` | 装了 TensorRT 11（cu13） | 卸掉，装 `tensorrt-cu12>=10,<11` |
| `libcudnn.so.9: cannot open` | 库路径没挂 | 执行 §5.1 的 `LD_LIBRARY_PATH` |
| 导出 fp16 报 `mixed dtype (CPU)` | 把 PyTorch 模型 `.half()` 了 | 导 fp32 后在 ONNX 图层面转 fp16 |
| `Unexpected input data type: expected float16` | fp16 模型喂了 float32 输入 | 输入也转 fp16 |
| ORT/TRT 数字异常好看或异常难看 | provider 静默回退 | 看脚本打印的「实际后端」与 `provider_ok` 字段 |
| CPU 加速比 1.6× 但复核只有 1.06× | PyTorch 少用了线程 | `--torch-threads` 与 `--ort-threads` 设成相同值 |

### 5.5 建议的 smoke 顺序

先小规模验证再全量：

1. **导出**：先只导图像塔 fp32，看余弦是否 ≥0.999（脚本自动校验）；

### 5.9 七个坑

1. registry 里的权重路径必须能解析，否则评测读不到编码器；
2. 建索引与评测的 `quant` 必须一致（同源原则；错了不报错，但指标全废）；
3. INT8 动态量化是 CPU 路径，`--device cuda` 加不上；
4. 5060 Ti 是 sm_120，4-bit 要新版 `bitsandbytes`；TensorRT 要 10.x；
5. 先 smoke（手机壳 300 条）再全量 9,393 张；
6. ONNX 导出图像塔与文本塔要**分开**，文本塔给动态序列长度；
7. `data/index_data/鞋/鞋/` 是重复的整份鞋索引（27MB，被 git 跟踪），对比新旧索引前先删。

## 九、风险与退路

| 风险 | 退路 |
|---|---|
| 4-bit 装不上（sm_120） | 退成 FP16 vs INT8 两组，报告写明原因 |
| ViT 静态量化算子不支持（LayerNorm/GELU） | 图像塔改动态量化或 FP16，文本塔保持动态量化；报告写清取舍 |
| INT8 全量 9,393 张太慢 | 先出体积/延迟结论，精度那栏补跑；或抽样并在报告写明抽样口径 |
| ONNX 导出文本塔报动态轴错误 | 固定序列长度导出（实验一模板文本长度固定，影响可控） |
| TensorRT / OpenVINO 装不上 | 只报 ONNX Runtime 一路，报告写明「未做及原因」 |
| 非训练机没有权重 | 不用传原始权重；做异构验证时传量化后的 ONNX（体积小得多） |
| 不同精度向量混用 | 一律整类重建索引（仓库 README 已写死「换模型必须重新提向量」） |

## 一、本组口径

任务书用 CIFAR-10 / 技术博客文本举例，本组沿用实验 1–4 对象：**电商商品图文 + Chinese-CLIP 双塔检索**。实验五在此基础上加 Agent 层：LLM 只做意图解析与工具调用，商品事实全部来自自有 9,393 条库与双塔接口，不编造。

闭环：实验1 数据 → 实验2 微调（LoRA）→ 实验3 优化（量化）→ 实验4 API（双塔接口）→ **实验5 Agent**（LangChain 调实验4 API）。

## 五、报告口径红线

- 任务是模板举例，本组按电商图文 + 双塔 Agent 口径写，不照抄 CIFAR-10 / ResNet。
- Agent 的 LLM 只做意图解析，商品事实来自双塔接口；不声称模型编造商品。
- 延迟/准确率数字标清后端（CPU/GPU）与机器；量化 4-bit 目标≤5 秒、10 轮准确率≥90%。
- 未做部分如实注明，不声称已测。

### 10.3 报告里必须如实写的三件事

**① 验证集只有 11 条，tool_call 仅 1 条 —— 该单项百分比不具统计意义。**
任务书要求的「10 轮工具调用准确率 ≥90%」必须在 5.4 端到端联调时用真实 10 轮对话测，
不能拿这 1 条充数。

**② tool_call 原始 0% 的真实原因：工具名拼错，参数全对。**
唯一验证样本把 `text_search` 输出成 `tool_search`，`query`/`category`/`top_k` 三个参数
全部正确。训练集 tool_call 仅 14 条，4B 模型没记牢专有名词。运行时纠错（5.3 的
`closest_tool`）能修正，但**评测口径不改**——报告里的 0% 就是真实成绩。

这恰恰是个好工程案例，适合写进「问题与解决方案」：白名单工具名约束 +
编辑距离纠错 + 采样不足的归因分析。

**③ 基座选型推翻了方案文档的原始候选。**
方案里写的 DeepSeek-V4.1-Flash（**763B**）、GLM-5.3（**753B**）、GLM-5.3-Flash（**321B**）
经 HuggingFace 实际核对均为数百 B 的 MoE，全参/LoRA 都超出本组资源，不可行。
改用 Qwen3-4B-Instruct-2507。这个决策理由要写进 5.2.1「选型与评估」。

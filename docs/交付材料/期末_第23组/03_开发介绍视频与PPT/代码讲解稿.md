# 第一部分 · 后端代码从哪走到哪（0:30–3:30）

## 1.1 启动走向（0:30–1:10）

**画面**：仓库根目录
**操作**：打开 `scripts/start_all.py`，鼠标划过文件头注释，不展开函数

**口播**：

先讲启动，因为启动决定了后面所有对象从哪来。

一键启动脚本是 `scripts/start_all.py`。它做三件事：检查虚拟环境和 ONNX 产物、起后端 uvicorn、起前端 Vite。后端真正的入口写在命令里：`uvicorn app.main:app`。

所以链路是：

```text
scripts/start_all.py
        ↓  uvicorn app.main:app
webapp/backend/app/main.py  :  create_app()
        ↓
include_router(v1 / tasks / admin / agent)
        ↓
lifespan 后台预热 Agent 模型
```

`main.py` 只装配，不写业务。四组路由注册完，服务就起来了。Agent 模型在 `lifespan` 里**后台线程预热**，加载失败只记日志，不影响其他接口——这是故意设计的，模型挂了服务也得能用。

## 1.2 一次文本搜索的走向（1:10–2:20）★

**画面**：VS Code，按下面的顺序快速切换文件，每个文件停 3～5 秒
**操作**：`api/v1.py` → `deps.py` → `matching.py` → `encoder.py` / `index_store.py` → 回到 `api/v1.py`

**口播**：

现在走一条真实请求。前端输入「白色运动鞋」，点搜索：

```text
浏览器  POST /api/v1/text
   ↓  Vite 代理到 127.0.0.1:8000
api/v1.py : search_text()          ← 接参数、校验
   ↓  Depends(get_match_service)
deps.py   : 单例装配 encoder + index
   ↓
matching.py : MatchService.search_text()   ← 业务编排
   ├─ encoder.py   : encode_text()   → 512 维向量
   └─ index_store.py : best_category() → search() → top-k
   ↓
schemas.py : {code, result, msg}
   ↓
前端 client.js 拦截器解包
```

注意三个分界点：

第一，`api/v1.py` 不碰模型。它只把 `query`、`top_k`、`category` 交给 `MatchService`。

第二，`MatchService` 不碰 HTTP。它只依赖 `Encoder` 和 `IndexStore` 两个抽象，所以能单独测。

第三，`IndexStore` 不重算向量。它只读实验二、实验三已经做好的索引文件。

这三个分界点，就是后面要讲的三个关键设计。

## 1.3 Agent 请求的走向（2:20–3:00）★

**画面**：`api/agent.py` → `services/agent_service.py` → `scripts/agent/tools.py` → 回到 `agent_service.py`

**口播**：

Agent 是另一条链路，但结构一样：

```text
POST /api/v1/agent/chat
   ↓
api/agent.py : agent_chat()
   ↓
agent_service.py : AgentService.chat()
   ├─ _decide()        → 模型出 JSON 动作，或规则降级
   ├─ _run_tool()      → 调白名单工具
   │     └─ scripts/agent/tools.py : text_search()
   │           └─ HTTP 回调本机 /api/v1/text
   ├─ _render_tool_result() → 回喂结果、生成点评
   └─ _remember()      → 写会话历史与槽位

{reply, thinking, tool_calls, items}
```

这里最值得先记住一句：**Agent 调工具不是直接调函数，而是 HTTP 回调自己的 `/api/v1/text`**。这样 `scripts/agent` 可以独立环境运行，也能单独评测，跟后端解耦。

# 第二部分 · 具体代码（3:30–10:30）

> 每个文件只展开要讲的函数，其余折叠。口播里的代码是**删减过的骨架**，现场对着真实文件讲即可。

## 2.1 `main.py`：只装配，不写业务（3:30–4:10）

**画面**：`app/main.py`，展开 `create_app()`

**大致代码**：

```python
def create_app() -> FastAPI:
    app = FastAPI(title="Agent ShopVision API", lifespan=_lifespan)
    app.add_middleware(CORSMiddleware, allow_origins=settings.cors_origins, ...)
    app.include_router(v1.router)
    app.include_router(tasks.router)
    app.include_router(admin.router)
    app.include_router(agent.router)
    _register_handlers(app)          # 统一异常 → {code, result, msg}
    app.mount("/item-images", StaticFiles(...))
    return app
```

**口播**：

`create_app` 里没有一行编码或检索。它做四件事：建 app、开 CORS、挂四组路由、注册全局异常。

静态图片挂了三套：清洗图、上传原图、原始商品图。为什么分开？因为它们的生命周期不一样：清洗图是实验一产物，上传图是运行产物，原始图是只读素材，混在一起会互相污染。

异常处理也在这：业务异常、参数校验异常、404、未捕获异常，最后都转成 `{code, result, msg}`。未捕获异常只把类型写进服务端日志，不把堆栈回给前端——内部路径不外泄。

## 2.2 `api/v1.py`：路由是薄薄一层（4:10–5:00）★

**画面**：`app/api/v1.py`，展开 `search_text` 和 `_decode_image`

**大致代码**：

```python
@router.post("/text")
def search_text(payload: TextQueryRequest,
                service: MatchService = Depends(get_match_service)):
    return TextResponse.ok(
        service.search_text(payload.query, payload.top_k, payload.category)
    )
```

**口播**：

看这个函数，一共三行：接 Pydantic 校验过的参数、交给 service、套返回体。

所有上传接口还会先过 `_decode_image`，它集中做四件校验：大小不超过 10 MB、不是空文件、PIL 能解析、格式是 PNG/JPG/WEBP。校验只写一次，三个上传接口共用。这就是「校验放在入口，不要散在每个业务里」。

路由上的 `summary`、`description`、`responses` 不是给人看的注释，是给 `/docs` 生成 OpenAPI 文档用的。所以接口文档不用手写，改代码就同步更新。

## 2.3 `deps.py`：对象只建一次（5:00–5:30）

**画面**：`app/deps.py`

**大致代码**：

```python
@lru_cache(maxsize=1)
def get_encoder() -> Encoder:
    return build_encoder(get_settings())

@lru_cache(maxsize=1)
def get_index() -> IndexStore:
    return IndexStore(settings.index_path, upload_store=get_upload_store(), ...)
```

**口播**：

路由里只写 `Depends(get_match_service)`，不自己 new。好处有两个：换实现只改这一处；测试里用 `dependency_overrides` 一行替换，不用 mock 一堆东西。

## 2.4 `matching.py`：业务编排都在这（5:30–6:40）★

**画面**：`app/services/matching.py`，依次展开 `search_text`、`match`

**大致代码（文本检索）**：

```python
def search_text(self, text, top_k=5, category=None):
    vector = self.encoder.encode_text(text)
    query_category, query_score, _ = self.index.best_category(vector)

    if category and query_category and category != query_category:
        hits = []                       # 语义冲突，不硬凑
    else:
        hits = self.index.search(vector, [category] if category else None, top_k)

    return {"query": text, "category": ..., "query_category": query_category, ...,
            "items": [hit.as_dict() for hit in hits]}
```

**口播**：

这是整个后端的业务中心。以文本检索为例，四步：

编码、让文本塔自己判类、处理「用户限定类别」和「模型判出类别」的冲突、检索 top-k。

重点讲冲突这一步。如果用户限定「鞋」，但文本塔判出来是「包」，我们直接返回空。理由是：两条信息没有交集，硬返回包类商品等于骗用户。这个判断同时给前端做冲突提示。

**画面**：切到 `match` 函数

**大致代码（图文匹配）**：

```python
def match(self, image, text, top_k=5):
    image_vector = self.encoder.encode_image(image)
    text_vector = self.encoder.encode_text(text)
    image_category, _, image_scores = self.index.best_category(image_vector)
    text_category, _, text_scores = self.index.best_category(text_vector)
    hits = self.index.search(text_vector, top_k=top_k)
    return {"match": image_category == text_category, ...}
```

**口播**：

图文匹配更短，但设计点很关键：图像和文本**各自编码、各自判类**，最后只比顶层大类。

为什么不用图像判出的类别去限定文本检索？因为那样比对就恒为一致，等于循环论证。代码注释里也专门写了这一点。

细分类两边可能不一样——图判「跑步鞋」、文判「高帮运动鞋」——页面只比大类，所以结论还是一致。这是产品口径，也是代码有意为之。

## 2.5 `encoder.py`：第一个接缝（6:40–7:30）★

**画面**：`app/services/encoder.py`，先看抽象类，再看 `build_encoder`

**大致代码**：

```python
class Encoder(ABC):
    dim: int
    model_loaded: bool
    model_tag: str

    @abstractmethod
    def encode_image(self, image) -> np.ndarray: ...
    @abstractmethod
    def encode_text(self, text) -> np.ndarray: ...

def build_encoder(settings) -> Encoder:
    if settings.model_backend == "onnx":
        return OnnxEncoder(visual_path, text_path, provider=...)
    return PlaceholderEncoder(dim=settings.embedding_dim)
```

**口播**：

整个服务只依赖这两个方法：图像出向量、文本出向量。下面两档实现：

- 占位版：哈希输入、固定种子生成向量。不用 GPU、不用装模型，前后端和 CI 都能跑。
- ONNX 版：加载实验三的双塔，真正推理。

切哪一档，只由 `.env` 里 `SHOPVISION_MODEL_BACKEND` 决定。接口形状完全不变。

这里还要讲两个防错设计。

第一，`model_loaded`。占位模式是 `False`，`health` 接口如实返回，前端提示「结果无意义」，商品入库直接拒绝。我们不假装占位结果能用。

第二，`model_tag`。它把模型文件名、内容 sha256、输入尺寸拼成指纹，入库时写进 SQLite。换模型后，新向量不会和旧库混在一起。

## 2.6 `index_store.py`：第二个接缝（7:30–8:40）★

**画面**：`app/services/index_store.py`，展开 `_load`、`search`、`best_category`

**大致代码**：

```python
def _load(self, category):
    if category in self._cache:                 # 命中缓存直接返回
        return self._cache[category]
    with self._lock:
        self._cache[category] = self._read(category)
    return self._cache[category]

def search(self, vector, categories=None, top_k=5):
    self.check_dimension(vector)                # 维度不对 → 40003
    pool = []
    for category in categories or self.categories:
        items, embeddings = self._load(category)
        sims = embeddings @ vector               # 已归一化 → 点积 = 余弦
        idx = np.argpartition(-sims, k - 1)[:k]  # 取前 k
        pool += [Hit(category, i, sims[i], items[i]) for i in idx]
    pool.sort(key=lambda h: h.score, reverse=True)
    return pool[:top_k]
```

**口播**：

先澄清一个容易被问的点：**建库脚本用 FAISS，线上检索没有用 FAISS**。

线上只读三样：注册表、每类的 `items.csv`、每类的 `image_embeddings.npy`。因为实验二产出的向量已经 L2 归一化，余弦相似度就等于点积，所以直接 `embeddings @ vector`，再用 `argpartition` 取前 k。

九千三百九十三条、九类、512 维，numpy 足够快，还少一个线上依赖。真扩容再切 FAISS，`search` 的入参和返回值不用变。

两个细节：

第一，懒加载。每个类别第一次被查才读进内存，之后走缓存；首次加载加锁，避免并发重复读。

第二，维度校验。查询向量和索引维度不一致，直接返回 `40003`，不让矩阵乘法抛异常、最后变成 500。错误要错得明白。

## 2.7 `errors.py` + `schemas.py`：契约（8:40–9:10）

**画面**：`app/errors.py` 的码表 + `schemas.py` 的 `ApiResponse`

**大致代码**：

```python
class ErrorCode(IntEnum):
    OK = 0
    BAD_REQUEST = 40000
    INVALID_IMAGE = 40001
    DIM_MISMATCH = 40003
    CATEGORY_NOT_FOUND = 40401
    MODEL_UNAVAILABLE = 50001

    @property
    def http_status(self) -> int:
        return 200 if self is ErrorCode.OK else int(self) // 100

class ApiResponse(BaseModel):
    code: int = 0
    result: Any = None
    msg: str = "ok"
```

**口播**：

前后端只共用这一份契约。

五位业务码，前三位就是 HTTP 状态码：`40001` 对应 400，`40401` 对应 404，`50001` 对应 500。这样既满足任务书「400 参数错、404 路径错、500 服务器错」，又保留了细分场景。前端按前三位兜底，按整段码精确提示。

所有成功和失败都是同一种形状，前端一个拦截器就能处理完。

## 2.8 `agent_service.py`：模型只做意图（9:10–10:10）★

**画面**：`app/services/agent_service.py`，展开 `chat`、`_decide`、`_run_tool`、`_guard_reply`

**大致代码（删减骨架）**：

```python
def chat(self, message, session_id=None):
    messages = [system] + self._history(session_id) + [user(message)]
    action, thinking = self._decide(message, messages)

    if action["action"] == "reply":                # 模型选择直接回答，不检索
        return self._reply(self._guard_reply(action["text"]), ...)

    tool = action.get("tool") or "text_search"
    arguments = self._sanitize_tool(tool, action.get("arguments") or {})
    result, error = self._run_tool(tool, arguments)  # 失败重试 3 次
    reply = self._render_tool_result(tool, result, items, ...)
    self._remember(session_id, turns)
    return {"reply": reply, "thinking": thinking, "tool_calls": [...], "items": items}
```

**口播**：

这段是实验五的核心。原则一句话：**模型只决定调什么工具、传什么参数，商品事实不由它生成。**

`_decide` 让微调的 Qwen3-4B 输出 JSON 动作，只有 `tool` 和 `reply` 两种。

如果是 `tool`，先过 `_sanitize_tool`：工具名必须在白名单、类目必须是九个之一、`top_k` 夹到 1～50。然后 `_run_tool` 执行；`text_search` 带三次重试和日志——任务书要求的重试就落在这。

工具返回后，第二轮把商品字段回喂给模型写点评。点评必须在 10～300 字之间，含价格或销量断言直接退回模板。

**画面**：光标停在 `_guard_reply` 的正则

**口播**：

安全闸在这里。模型如果说「这款鞋 199 元」，正则直接命中，整段替换成安全话术。**不许编事实，是代码强制的，不是靠提示词自觉。**

**画面**：光标停在 `_remember` / `_merge_query`

**口播**：

多轮不赌 4B 的记忆。上一轮类目记在槽位里，用户说「要白色的」，检索词合并成「运动鞋 白色」；历史只留 8 条，另外把用户原话压成最多 6 句摘要塞回 system。会话 30 分钟过期、最多 500 段。

一句话：**记忆是工程逻辑，不指望参数量。**

> 被问到 LangChain：任务书 5.3 要求的 `create_agent` 版在 `scripts/agent/langchain_agent.py`，用 `@tool` 封装、`InMemorySaver` 隔离多轮；线上 5.4 走 `AgentService`，为了三档降级、重试和统一返回体。工具契约一致。

# 附 1 · 3 分钟极简版

**口播**：

后端走向一条线：`start_all.py` 起 `uvicorn app.main:app`，`main.py` 只装配路由和异常处理；请求进 `api/v1.py`，路由只接参数；业务在 `services/matching.py`，它调两个接缝——`encoder.py` 出 512 维向量，`index_store.py` 做点积取 top-k；最后统一返回 `{code, result, msg}`。

两个接缝都用配置切换：模型 `placeholder / onnx`，索引换目录只改 `deps.py`。线上检索不依赖 FAISS 和 PyTorch，只读实验二、实验三做好的文件。

Agent 多一条链：`api/agent.py` → `agent_service.py`。模型输出 JSON 工具调用，后端执行工具，再把结果回喂写点评。工具名有白名单纠错，参数有规范化，价格和销量断言有正则拦截，模型挂了降级规则解析。多轮槽位由代码维护。

前端一个 axios 拦截器统一解包，八个路由对应八个页面。

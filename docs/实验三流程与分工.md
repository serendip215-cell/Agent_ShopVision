> **依据**：开课讲稿 [`1开课.pdf`](1开课.pdf) 第 5、8 页——实验三 = 算法优化，学时 4，关键产出「轻量化模型 + 精度-速度等优化指标对比报告」；开发文档 [`电商商品多模态推荐与上架Agent开发文档.md`](电商商品多模态推荐与上架Agent开发文档.md) §6、§18.2。
>
> **主线一句话**：**凡是要 torch、要权重、要跑模型的事，全在训练机上做——包括写和改代码。** 不需要环境的（写报告、出图、交付材料、编译 PDF）在非训练机上做。
> 训练机 = RTX 5060 Ti 8GB 那台，容器 `shopvision`，仓库在容器内是 `/workspace`，有全部权重和官方代码；非训练机 = 现在的这台（RTX 3050 Ti 4GB），没有权重、没有 torch/cn_clip。

## 〇、一页总流程

```text

────────────────────────────────────────────────    ────────────────────────────────
P0  环境自检 + git pull
P1  写/改量化代码 → 当场自测（smoke）→ git push  ───────▶

                                                            + 交付材料 + 编译 PDF
P6  现场演示 / 录屏（要跑模型，只能在训练机）
```

| 阶段 | 在哪台 | 做什么 | 产出 | 前置 | 粗估 |
|---|---|---|---|---|---|
| P0 | 训练机 | `git pull` + 环境自检（torch/cuda/faiss/cn_clip/bnb） | 环境检查输出 | — | 10 分钟 |
| P1 | 训练机 | 写/改量化代码（§2.2 六处）+ smoke 自测 + `git push` | 代码、3 份 config | P0 | 1–2 小时 |

| P3 | 训练机 | B 组 INT8、C 组 4-bit：建索引 + 评测 | `exp3_ft_int8`、`exp3_ft_nf4` + 两套索引 | P1 | 半天 |
| P4 | 训练机 | bench（体积/显存/启动/延迟/吞吐）+ 索引核验 + 归档 `git push` | `docs/optimize/runs/<RUN>/` + `exp3_ft_*` | P2、P3 | 1 小时 |

## 一、为什么代码也在训练机上写

| 理由 | 说明 |
|---|---|
| 非训练机没法自测 | 本机没有 torch、没有 `cn_clip`、没有权重。代码改完连 `python -c "import torch"` 都过不去，只能盲写盲推，到训练机才炸，来回折腾 |
| 训练机的 clone 就是可写的 git 仓库 | 实验二的微调代码和索引就是从它推的（`8fc67a70`、`c6a8792e`、`79e23eb4`，作者 `wangluzhou`），不需要额外配置 |
| 现场的坑要一边跑一边解 | 索引 registry 里的权重路径、编码器同源、sm_120 上的 bitsandbytes 版本——这些只有在那台机器上才能验证 |
| 代价可控 | 非训练机失去「改代码」的能力，但**改文档和报告不受影响**（Typst、`docs/`、README 都不碰 torch） |

结论：**代码 + 实验一起在训练机做，非训练机只做文档与交付。**

## 二、训练机（P0–P4，命令可照抄）

容器名 `shopvision`，仓库在容器内 `/workspace`。命令从 WSL 宿主机发起；`.sh` 脚本要 `tr -d '\r'` 清 Windows 换行符（仓库既有做法，见 `scripts/finetune/README.md`）。

### 2.1 P0 环境自检

```bash
wsl -d Ubuntu-22.04
docker exec -it shopvision bash -lc "cd /workspace && git pull && export PYTHONPATH=/workspace/Chinese-CLIP && \
  python -c \"import torch,timm,faiss,cn_clip.clip as c;print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name())\""
```

- `torch.cuda.is_available()` 必须 `True`；`cn_clip` 靠 `PYTHONPATH` 指向官方代码，**不要**再 `pip install cn_clip`。
- 缺 `faiss`/`timm`：`pip install -r /workspace/scripts/retrieval/requirements.txt`。
- 4-bit 组开跑前：`pip install -U "bitsandbytes>=0.46"`（5060 Ti 是 sm_120）。

### 2.2 P1 要改的六处代码

| # | 文件 | 改什么 |
|---|---|---|
| 1 | `scripts/retrieval/encoder.py` | `ChineseClipEncoder` 加 `quant` 参数（`fp16` / `int8` / `nf4`），实现挂在第 108 行 `self.model.eval()` 之后。建索引、查询、评测三条链路都过这个类，改一处全带上 |
| 2 | `scripts/retrieval/build_category_index.py` | 加 `--quant` 命令行参数，并把 `quant` 写进 `index_registry.json` 的 `model` 段 |
| 3 | `scripts/retrieval/configuration.py` | 已通用，只需保证 `build` 和 `search` 两段的 JSON 能通过字段校验（新增字段必须先在脚本里有对应 `--参数`，否则会报「不支持的字段」） |
| 4 | `evaluation/retrieval/code/evaluate_retrieval.py` | 读 `index_registry.json` 的 `model.quant`（现在读的是 `model.checkpoint`，见 522–530 行），传给编码器 |
| 5 | `scripts/retrieval/search_category_index.py` | 同上 |
| 6 | `scripts/optimize/bench_inference.py` | 新建：模型体积、峰值显存（`torch.cuda.max_memory_allocated()`）、启动时间、单次编码延迟（ms/图）、吞吐（图/秒），输出 JSON |

同时产出 3 份配置 `configs/retrieval_exp3_{fp16,int8,nf4}.json`，每份从 `configs/retrieval.json` 复制，只改两处：

```jsonc
{
  "build":  { "output_dir": "data/index_data_exp3_nf4",
              "checkpoint": "data/processed_data_retrieval/experiments/2026-10-18_bs32_lr1e-5/checkpoints/epoch3.pt",
              "quant": "nf4" },
  "search": { "index_dir":  "data/index_data_exp3_nf4", "quant": "nf4" }
}
```

**同源原则**：查询编码器与索引向量必须同一权重、同一精度。评测脚本从索引的 registry 取编码器，`build` 时必须把 `quant` 写进 registry，否则会拿 FP16 编码器去搜 INT8 索引，指标全废。

### 2.3 P1 先跑 smoke，再跑全量

```bash
# 用最小的类别（手机壳 300 条）先跑通整条链路，别一上来就 9,393 张
docker exec -it shopvision bash -lc "cd /workspace && export PYTHONPATH=/workspace/Chinese-CLIP && \
 python scripts/retrieval/build_category_index.py --config configs/retrieval_exp3_int8.json \
   --categories 手机壳 --output-dir data/index_data_exp3_int8_smoke --overwrite"
```

smoke 能过（索引出来、`ntotal` = 记录数、评测能跑完）再推代码、再上全量。

### 2.4 P2 A 组（FP16 基线）

```bash
docker exec -it shopvision bash -lc "cd /workspace && export PYTHONPATH=/workspace/Chinese-CLIP && \
 python evaluation/retrieval/code/evaluate_retrieval.py \
   --config configs/retrieval.json \
   --index-dir data/index_data_finetuned \
   --queries evaluation/retrieval/results/runs/deepseekv4_1_flash_pilot_20261018/inputs/queries.csv \

   --run-id exp3_ft_fp16 --top-k 10 --candidate-k 50 --device cuda"
```

索引现成不用重建。把 `--index-dir` 换成 `data/index_data`、`--run-id exp2_pt_vs_ft_e2e` 再跑一次，顺手补上 README「还没做」里那条端到端新旧索引对比（选做加分）。

### 2.5 P3 B / C 组

```bash
# 建索引（9,393 张分批判码；INT8 是 CPU 路径，会慢）
docker exec -it shopvision bash -lc "cd /workspace && export PYTHONPATH=/workspace/Chinese-CLIP && \
 python scripts/retrieval/build_category_index.py --config configs/retrieval_exp3_int8.json --overwrite"

# 评测（编码器由该索引 registry 的 quant 决定）
docker exec -it shopvision bash -lc "cd /workspace && export PYTHONPATH=/workspace/Chinese-CLIP && \
 python evaluation/retrieval/code/evaluate_retrieval.py \
   --config configs/retrieval_exp3_int8.json --index-dir data/index_data_exp3_int8 \
   --queries <同上 queries.csv> --qrels <同上 qrels.csv> \
   --run-id exp3_ft_int8 --top-k 10 --candidate-k 50 --device cpu"
```

4-bit 那组同理，配置换 `configs/retrieval_exp3_nf4.json`、`--device cuda`。装不上 bitsandbytes 就如实退成 FP16 vs INT8 两组，并把报错写进记录。

### 2.6 P4 bench + 核验 + 归档

```bash
docker exec -it shopvision bash -lc "cd /workspace && export PYTHONPATH=/workspace/Chinese-CLIP && \
 python scripts/optimize/bench_inference.py \
   --checkpoint data/processed_data_retrieval/experiments/2026-10-18_bs32_lr1e-5/checkpoints/epoch3.pt \
   --quant nf4 --device cuda --batch-size 16 --images 200 \
   --out docs/optimize/runs/2026-10-XX_exp3/bench_nf4.json"
```

核验（每组都做）：向量数 = 记录数 = FAISS `ntotal`；随机抽 10 条 `vector_id → item_id → 图片` 能对上。核验记录写进 `docs/optimize/runs/<RUN>/`。

归档与推送：

| 产物 | 去哪 | 入 git？ |
|---|---|---|
| 索引目录（3 套 × ~78MB） | 训练机本地 `data/index_data_exp3_*/` | ❌ 太大，脚本可重建 |
| 量化后权重（FP16 ~376MB / INT8 ~188MB / nf4 ~100MB） | 训练机本地 `models/chinese_clip/quant/` | ❌ 与实验二同口径，报告写路径 + 重建命令 |
| bench json、`summary.json`、`run_metadata.json`、日志、核验记录 | `docs/optimize/runs/2026-10-XX_exp3/` | ✅ |
| 评测结果 | `evaluation/retrieval/results/runs/exp3_ft_*/` | ✅ |
| 代码与 3 份 config | 正常提交 | ✅ |

### 2.7 六个坑

1. registry 里的权重路径必须能解析，否则评测读不到编码器；
2. 建索引与评测的 `quant` 必须一致（同源原则）；
3. INT8 动态量化是 CPU 路径，`--device cuda` 加不上；
4. 5060 Ti 是 sm_120，4-bit 要新版 `bitsandbytes`；
5. 先 smoke（手机壳 300 条）再全量，别一上来跑 9,393 张；
6. `data/index_data/鞋/鞋/` 是重复的整份鞋索引（27MB，被 git 跟踪），对比新旧索引前先删。

| 讲稿要求 | 落地 |
|---|---|
| 模型压缩（量化 / 剪枝 / 蒸馏）+ 推理加速 | 量化做满三组（FP16 / INT8 / 4-bit）；剪枝、蒸馏、ONNX 只当加分 |

## 五、实验设计（对象 / 对照 / 指标口径）

**被压对象**：实验二训出来的 Chinese-CLIP ViT-B/16（`epoch3.pt`），不是预训练权重，也不是实验五那条 Qwen2.5-VL 的线。

| 组 | 方案 | 设备 | 风险 |
|---|---|---|---|
| A | FP16 基线（锚点，必做） | CUDA | 无 |
| B | INT8 动态量化（`torch.quantization.quantize_dynamic`） | **CPU** | 9,393 张全量编码慢 |
| C | 4-bit nf4（bitsandbytes） | CUDA | sm_120 需要新版 bnb |
| 选做 | 剪枝 / ONNX / 图片缩放策略 | CUDA | 遇阻就跳过 |

**指标口径（表头，三组不许各调各的）**

- 精度：Recall@1 / 5 / 10、MRR@10、nDCG@10，同一份 queries/qrels（132 查询 / 1325 标签）、同 top-k=10 / candidate-k=50，取自 `query_metrics.csv` 与 `summary.json`；
- 资源：模型体积（MB）、峰值显存、启动时间、单次编码延迟（ms/图）、吞吐（图/秒）；
- 质量门：先定「Recall@1 掉 ≤2pp 算可接受」，实测后按真实曲线校准，别改阈值凑数；
- 融合权重与阈值沿用 `configs/retrieval.json`（`image_weight=0.7 / text_weight=0.3`）。

**资产分布**

| 东西 | 训练机 | 非训练机 |
|---|---|---|
| 预训练权重 719MB、微调权重 `epoch3.pt` | ✅ | ❌ |
| 清洗数据 9,393 张、两套现成索引、固定验证集、脚本 | ✅ | ✅（走 git） |
| torch / cn_clip / faiss | ✅ | ❌ |

## 九、风险与退路

| 风险 | 退路 |
|---|---|
| 4-bit 在 sm_120 上装不上 | 退成 FP16 vs INT8 两组，报告写明原因和影响 |
| INT8 全量 9,393 张太慢 | 先出「体积 + 延迟」的资源结论，精度那栏补跑；或改用 ONNX Runtime 的 INT8 |
| 量化后精度掉太多 | 把「掉了多少」当结论写，这正是「精度稳定性」维度的答案，不是失败 |
| 索引/权重路径错位导致评测报错 | 查 `index_registry.json` 的 `model` 段改路径，不要改脚本 |
| 不同精度向量混用 | 一律整类重建索引（仓库 README 已写死「换模型必须重新提向量」） |
| 非训练机想改代码 | 改文档随便；改代码请回训练机，或改完在训练机上验证后再 push |

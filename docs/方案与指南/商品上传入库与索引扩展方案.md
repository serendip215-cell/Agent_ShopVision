# 商品上传入库与索引扩展方案（SQLite）

> 状态：**方案，未实施**（2026-11-02）。本文定设计与边界，不代表代码已开工。
> 关联：[实验五-对话式导购助手方案.md](实验五-对话式导购助手方案.md)、[`webapp/API约定.md`](../../webapp/API约定.md)。

## 1. 目标

让开发者/管理员在 Web 端上传商品图，系统完成：

```text
上传图片 → ONNX 图像塔编码 → 给出建议类目 → 人工确认
        → 图片落盘 → 元数据 + 向量入库 → 立即可被检索/判类
```

一句话：**把现在只读的 9,393 条索引，扩展成可增量写入的商品库。**

## 2. 非目标

- 不做云端 MySQL；单机 SQLite 足够（理由见 §4）。
- 不做“模型自动发现新类别”；闭集模型没有这个能力，新类最多做到“建桶 + 阈值”，需人工确认。
- 不做多后端实例同时写入。
- 不做商品编辑/删除的完整后台，第一版只做新增与查询。
- 不改现有静态索引文件（`data/index_data_finetuned/` 保持只读）。

## 3. 现状与约束

| 项 | 现状 |
|---|---|
| 编码器 | `visual_fp32.onnx`，输出 512 维、已 L2 归一化 |
| 静态索引 | 9 类 9,393 条，每类 `items.csv` + `image_embeddings.npy` |
| 后端读取 | `IndexStore` 只读、按类懒加载、内存缓存 |
| 服务接口 | 3 个同步 + 3 个异步任务接口 |
| 鉴权 | 只有前端演示级管理员门禁，**后端无鉴权** |
| 数据库 | 无；Python 自带 `sqlite3`（已验证 3.45.1），零安装 |

## 4. 为什么选 SQLite

上传功能引入了写入，CSV + npy 顶不住：

- 并发写两个文件没有事务，写坏即索引损坏；
- `.npy` 文件头记录行数，追加要整文件重写；
- 没有唯一约束，重复上传防不住；
- 没有审计记录，失败原因查不了。

SQLite 提供事务、唯一约束、单文件零运维。**不选 MySQL**：单后端、单机写入，云端 MySQL 只会增加连接、账号、网络延迟与答辩故障点。只有将来多实例同时写才需要考虑 MySQL。

## 5. 存储设计

### 5.1 数据库文件

```text
data/webapp.db          # SQLite 主文件
data/webapp.db-wal      # WAL 模式自动生成
data/webapp.db-shm
```

启用 `PRAGMA journal_mode=WAL`、`PRAGMA foreign_keys=ON`、`busy_timeout=5000`。

### 5.2 表结构

```sql
CREATE TABLE categories (
  name       TEXT PRIMARY KEY,
  created_at TEXT NOT NULL
);

CREATE TABLE items (
  item_id          TEXT PRIMARY KEY,
  category         TEXT NOT NULL REFERENCES categories(name),
  item_name        TEXT,
  product_type     TEXT,
  type             TEXT,
  color            TEXT,
  material         TEXT,
  brand            TEXT,
  description      TEXT,
  local_image_path TEXT NOT NULL,
  vector           BLOB NOT NULL,   -- float32[512]，L2 归一化
  model_tag        TEXT NOT NULL,   -- 例：visual_fp32.onnx + 文件哈希
  created_at       TEXT NOT NULL
);

CREATE INDEX idx_items_category ON items(category);

CREATE TABLE ingest_log (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  item_id    TEXT,
  action     TEXT NOT NULL,         -- upload / reject
  status     TEXT NOT NULL,         -- ok / error
  message    TEXT,
  created_at TEXT NOT NULL
);
```

要点：

- **`model_tag` 必存**。换模型后旧向量与新向量不在同一空间，混用会静默出错。
- 向量以 BLOB 存，9,393 条约 19 MB，SQLite 无压力；启动时读入内存矩阵。
- `item_id` 建议 `upload_<sha256(图片)[:12]>`，同时以图片 SHA-256 去重；重复上传直接返回已有条目。
- 图片存 `data/processed_data_cleaning/<类>/images/<item_id>.<ext>`，数据库只存相对路径。
- 上传条目不回写 `items.csv`；**SQLite 是上传数据的唯一事实来源**，静态索引保持只读。若将来需要离线重建，另写导入脚本。

## 6. 检索层设计

采用「静态索引 + 动态条目合并」，避免改动现有只读索引：

```text
IndexStore（静态，只读）
   + UploadStore（SQLite，动态）
   → 每类：items 字典 + 向量矩阵合并
   → search() / best_category() 对两者一视同仁
```

- 启动时把 SQLite 条目按类加载进内存；
- 新增成功后调用 `reload(category)`，原子替换该类的缓存，不重启服务；
- `health` 的类别条数 = 静态 `registry.items` + 动态条目数；
- 动态向量同样做 L2 归一化，维度与静态索引不一致时直接报 `40003`，不静默拼接。

## 7. 接口设计

### 7.1 新增商品

```http
POST /api/v1/admin/items
Content-Type: multipart/form-data

file:        商品图（必填，沿用 10 MB / PNG·JPG·WEBP 校验）
category:    目标类别（可选；不传则返回建议类目，不入库）
item_name:   商品名（可选）
type/color/material/brand/description: 可选
confirm:     true 才真正入库
```

行为：

1. 校验图片格式与大小；
2. `encode_image` 编码；
3. 未传 `category` 或 `confirm != true`：调 `best_category` 返回建议类目 + 置信度，**不写任何数据**；
4. 传了 `category` 且 `confirm=true`：写图片临时文件 → SQLite 事务插入 → rename 到正式路径 → 刷新索引缓存；
5. 返回 `item_id`、`category`、`similarity`、`created_at`。

失败处理：任一步失败回滚事务并清理临时文件；重复图片返回已有 `item_id`，不重复入库。

### 7.2 查询入库结果（可选）

```http
GET /api/v1/admin/items/{item_id}
```

### 7.3 鉴权

后端目前没有鉴权，管理接口不能裸奔。第一版二选一：

- 只监听本机（`127.0.0.1`），管理接口仅本机可访问；
- 或加环境变量 `SHOPVISION_ADMIN_TOKEN`，请求头 `X-Admin-Token` 校验；token 不进前端代码。

**不要复用前端那个写死的演示密码。**

### 7.4 配套字段（前端假数据收口）

| 接口 | 新增字段 | 用途 |
|---|---|---|
| `GET /health` | `category_counts: {类别: 条数}`、`total_items` | 首页/状态页不再写死 9,393 与各类条数 |
| `POST /match` | `image_type` | 替换 MatchLab 的假细分类「女士小板鞋」 |

`category_counts` 来自注册表 + SQLite 动态计数；`image_type` 取图像塔在预测类别内 top-1 商品的 `type`，语义是“最相似商品的细分类”，不是模型直接预测。

## 8. 新类别（P2，暂不做）

若将来要支持：

1. `POST /api/v1/admin/categories` 建空类别；
2. 新类至少 N 张样例图（建议 ≥5），否则不参与判类；
3. 加“未知”阈值：top-1 相似度低于 T 时返回“未知”，避免新类抢占原有结果；
4. 新类只影响检索/判类的候选集合，**不等于模型学会了这个类**，报告里必须写清。

## 9. 一致性与并发

- 单进程 + SQLite WAL 足够；FastAPI 同步路由在线程池，**每个请求开独立连接**，不共享全局 connection。
- 写入串行化：短事务 + `busy_timeout`；如开多 worker，管理写接口需文件锁或单独进程。
- 图片与数据库的顺序：先写临时文件 → 编码 → 事务插入 → rename 正式文件 → 提交；失败清理临时文件。
- 定期清理孤儿图片（有文件、无数据库行）与缺失图片（有行、无文件）的巡检脚本可选。

## 10. 分阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 | SQLite 表 + UploadStore + 上传接口（仅已有 9 类）+ 合并检索 + reload | 上传后立即可被文搜/图搜命中；重启仍在；重复上传被拒 |
| P1 | `health.category_counts`、`match.image_type`、前端收口 | 首页/状态页数字来自接口；MatchLab 不再出现假细分类 |
| P2 | 新类别 + 未知阈值 + 审计查询 | 新类需人工确认，低置信度不误判 |

## 11. 测试

后端（临时 SQLite + 假编码器）：

- 正常上传：入库、计数 +1、可检索；
- 重复图片：返回已有条目，不新增；
- 维度不符：`40003`，不写入；
- 类别不存在：`40401`，不写入；
- 事务失败：无残留行、无残留临时文件；
- 重启后动态条目仍在；
- `health.category_counts` 与 `match.image_type` 字段形状正确。

前端：

- 管理页上传 → 显示建议类目 → 确认 → 成功提示；
- 上传后刷新检索页能搜到新商品；
- 上传失败显示后端中文 `msg`。

## 12. 风险

| 风险 | 应对 |
|---|---|
| 新向量与旧模型不同源 | `model_tag` 校验，不一致拒绝写入 |
| SQLite 文件放临时磁盘/容器 | 持久卷；文档注明备份 = 复制 `.db` 文件 |
| 管理接口无鉴权 | 本机监听或 admin token |
| 闭集模型被误认为“会学新类” | 只开放已有 9 类；新类 P2 且报告写清边界 |
| 静态索引与 SQLite 双源 | 静态只读、动态唯一写入方，合并层统一排序 |
| 并发写坏库 | WAL + 每请求连接 + 短事务 + 单写者 |

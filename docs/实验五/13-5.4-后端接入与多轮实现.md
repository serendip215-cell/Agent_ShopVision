# 5.4 对话 Agent 后端接入与多轮实现（2026-11-09）

> 本文记录 5.4 阶段后端侧已完成的工作：动作协议、工具路由、两轮点评、多轮记忆、
> 清理机制、图搜接入多轮，以及实测中暴露的问题与修法。
> 训练侧（数据、超参、实跑）见 `11-5.4-v4多轮训练规范.md` 与 `12-v4多轮Agent训练实跑记录.md`。

---

## 1 目标

| 目标 | 验收口径 |
|---|---|
| 接口可用 | `POST /api/v1/agent/chat` 永远返回 `{code, result, msg}`，模型不可用时降级规则 |
| 会聊天也会检索 | 寒暄/能力询问走 `reply`；找商品走 `tool` |
| 四个工具 | `text_search` / `image_search` / `list_categories` / `get_item_detail` |
| 多轮 | 同一 `session_id` 下可省略类目（“要白色的”继承“鞋”） |
| 不编造 | 回复中不得出现具体价格、销量、品牌；命中则替换成安全话术 |

---

## 2 动作协议

模型只输出**一个 JSON**，二选一：

```json
{"action":"tool","tool":"text_search","arguments":{"query":"白色运动鞋","category":"鞋","top_k":5},"say":"我先帮你找找"}
{"action":"reply","text":"你好，能帮你找点什么？"}
```

- `say` 可选，≤30 字，只用于工具调用前的过渡语；
- 兼容 v2：模型只给 `{"tool":...,"arguments":...}` 时按 tool 动作处理；
- 工具名走白名单纠错（`tool_search` → `text_search`）。

解析层在 `scripts/agent/intent_parser.py`：

| 方法 | 用途 |
|---|---|
| `parse_action(text)` | 单轮决策（v3） |
| `parse_action_messages(messages)` | 多轮决策（v4），带完整历史 |
| `reply_messages(messages)` | 基于检索结果写点评 |
| `comment(text, items_json)` | 单轮点评（v3） |
| `normalize_action()` / `as_action()` | 统一成动作 / 包装规则结果 |

---

## 3 两轮流程

```
用户话
 └─ 决策：tool 或 reply
     ├ reply → 安全闸 → 直接回话（不检索）
     └ tool  → 参数校验 → 执行工具
                ├ 检索类：把结果按训练格式回喂 → 模型写点评 → 失败退回模板
                └ 类目/详情：结构化模板（不走模型）
```

- 回喂格式固定为 `检索结果：{"items":[…]}`（与训练数据同构，字段：category / item_id /
  item_name / type / color / material / similarity）；
- 点评长度限 20–200 字，命中价格断言则丢弃，改用模板。

## 4 多轮与记忆

### 4.1 会话状态

| 状态 | 存放 | 上限 |
|---|---|---|
| 历史消息 | `_sessions[session_id]` | 最近 8 条（约 2 轮检索对话） |
| 用户原话摘要 | `_summaries[session_id]` | 最多 6 句，每句 ≤40 字 |
| 槽位 | `_slots[session_id]` | `{category, query}` |
| 活跃时间 | `_seen[session_id]` | 用于 TTL / LRU |

摘要以一行追加到 system：`早前用户说过：找运动鞋；要白色的`。

### 4.2 查询合并

模型在多轮里常只给「白色」（训练数据的继承样本就是“颜色 + 继承类目”），单独检索太泛，
后端在同类目下把上一轮查询拼上：

```
上一轮 query=运动鞋, category=鞋
这一轮 query=白色,  category=鞋
→ 实际检索 query="运动鞋 白色", category=鞋
```

规则：类目必须相同；新查询已包含旧查询则不重复；换类目不合并。
`thinking` 会写「继承上一轮查询：运动鞋 白色」。

### 4.3 图搜进入多轮

`/agent/image` 接受 `session_id` 后，图搜结果写入历史：

```
user: 按这张图找类似的
assistant: {"action":"tool","tool":"image_search","arguments":{"alpha":0.6,"top_k":5}}
user: 检索结果：{"items":[…]}
assistant: {"action":"reply","text":"这张图看起来属于「鞋」……"}
```

同时写入槽位 `category=鞋`。由于 `image_search` 参数里没有 `category`，模型拿不到类目，
所以后端在下一轮 `text_search` 缺 `category` 时**用槽位兜底**，
`thinking` 显示「沿用上一轮类目：鞋」。

### 4.4 上下文预算

以 v4 训练长度 512 token 估算，一轮检索约占 330 token，因此：

- 历史压到 8 条；
- 历史里的检索结果只保留 3 个商品；
- 摘要 ≤6 句。

两轮检索对话约 450 token，落在训练分布内。

## 5 清理与容量

| 机制 | 触发 | 行为 |
|---|---|---|
| 前端「清空」 | 用户点击 | 调 `DELETE /api/v1/agent/session/{id}`，并换新 `session_id` |
| `drop_session()` | DELETE 接口 | 删除历史、摘要、槽位、时间戳 |
| TTL | 每次对话前 `_gc()` | 30 分钟不活跃的会话回收 |
| LRU | 同上 | 会话数 > 500 时淘汰最久未用 |

重启服务同样会清空（全部在进程内存，未落盘）。

## 6 模型与降级

| 层 | 行为 |
|---|---|
| 适配器探测 | `dist/lora_adapter_v4` > `v3` > `v2` |
| 提示词 | **从训练数据第一条 system 读取**（`dataset_system_prompt()`），保证训练/推理逐字一致 |
| 多轮开关 | 适配器名含 `v4` 时启用多轮与结果注入 |
| 降级 | 模型加载失败 → `rule_parse`；单次推理异常 → 规则动作；工具失败 → 模板文案 |

> 关键教训：训练数据生成后若再改脚本里的提示词，推理必须跟着数据走，否则模型行为会漂。

---

## 7 安全与纠偏

| 问题 | 处理 |
|---|---|
| 编造价格/销量（如「¥19.9，5000+人买过」） | 正则拦截，替换为安全话术 |
| 主语说反（“能/可以帮我找点什么吗”） | 正则改为「帮你」；v5 数据再在提示词里根治 |
| 查询带量词/客套（“找一双白色运动鞋”） | 去前缀、去量词 |
| “10 个” 被忽略 | 抽取数字覆盖 `top_k` |
| 类目/详情工具没有 items | 单独模板渲染，不套“没找到商品” |

## 8 接口与字段

| 方法 | 路由 | 关键字段 |
|---|---|---|
| POST | `/api/v1/agent/chat` | 入：`message`、`session_id?`；出：`reply/thinking/tool_calls/items/say` |
| POST | `/api/v1/agent/image` | 表单：`file`、`message?`、`alpha`、`top_k`、`session_id?`；出：`reply/items/category/similarity` |
| DELETE | `/api/v1/agent/session/{session_id}` | 出：`{"deleted": true}` |

前端：`sendAgentChat({message, sessionId})`、`sendAgentImage({..., sessionId})`、
`deleteAgentSession(id)`；对话历史与 `session_id` 存 `localStorage`，刷新不丢。

## 9 测试与实测

### 9.1 单测

`webapp/backend/tests/test_agent_api.py` 共 100 条（含接口层），覆盖：

- 动作分流（reply 不检索、tool 才检索）；
- 参数校验（空/超长 → 40000，`top_k` 夹紧，非法类目丢弃）；
- 工具失败重试 3 次并降级；
- 编造拦截、主语修正；
- 类目/详情渲染；
- 会话历史写入、8 条裁剪、摘要、槽位合并、TTL 回收、`drop_session`；
- DELETE 路由与图搜 `session_id` 透传；
- OpenAPI 12 个接口（含新增 DELETE 路由）。

### 9.2 多轮实测（v4）

`scripts/agent/dev_smoke_multiturn.py` 结果：

```
第 1 轮：找运动鞋 → category=鞋, query=运动鞋
第 2 轮：要白色的 → category=鞋（继承）, query=运动鞋 白色（合并）
第 2 轮结果类目：{'鞋'}
多轮继承：✅ 通过
```

### 9.3 实测暴露的问题与修法

| 现象 | 根因 | 修法 |
|---|---|---|
| 「要白色的」跨类目搜（水杯/收纳盒） | 单轮模式，未带历史 | 确认 adapter=v4、`session_id` 透传 |
| 「要白色的」检索为空 | 模型只给 query=白色 | 后端查询合并 |
| 「换成黑色的吧」（图搜后）混进包/厨房用品 | `image_search` 无 category，结果字段也不带类目 | 结果加 `category` + 槽位兜底 |
| 「可以帮我找点什么吗」 | v4 数据缺“客服口吻”规则 | 正则纠正；v5 数据补规则 |

## 10 已知边界（报告里如实写）

1. 检索没有相似度阈值，库外需求也会返回 top-k（相似度 0.35–0.42），**不能宣称“能识别库外”**；
2. 模型是纯文本，**看不到图**；图搜由图像塔编码 + 索引检索完成，模型只负责点评；
3. 多轮的“细节记忆”约 2 轮，更早只保留一句摘要；要更长需提高 `max_len` 重训；
4. 会话状态在进程内存，重启即丢；跨重启需落 Redis/SQLite；
5. 价格/品牌字段在索引里大多为空，回复不提供价格信息。

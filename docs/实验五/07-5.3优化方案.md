| 指标 | 结果 | 目标 | 判断 |

| 总体工具调用准确率 | 2/10 = 20% | ≥90% | 未达标 |

## 二、问题定位

### 1. 类目识别不足

模型能识别 `text_search` 和 `top_k`，但经常没有输出 `category`。例如“白色运动鞋”没有补出“鞋”，“红色带盖炒锅”没有补出“厨房用品”。这说明模型没有稳定学习自然语言商品词与项目类目之间的映射关系。

### 2. query 没有统一清洗

部分输出把“找”“有没有”等对话词保留在 query 中，导致 query 与标准答案不一致。例如“找卡其色立领夹克”被原样输出，没有规范为“卡其色 立领夹克”。

### 3. 无类目查询的边界不清晰

“随便看看有什么”属于无类目查询，但模型将 query 改写为“有什么”，与评测要求的保留原意不一致。需要明确无类目查询的处理规则。

### 4. 运行时降级掩盖了模型输出问题

模型出现空工具名时，系统会降级到规则解析。降级保证了系统可用，但没有解决模型本身的类目和 query 生成能力，因此评测仍然失败。

## 三、优化顺序

### 第一阶段：先优化解析约束，不立即重新训练

1. 在 system prompt 中明确输出 JSON schema：
   - `tool` 必须是 `text_search`
   - `arguments.query` 只保留商品特征词
   - `arguments.category` 必须从固定类目集合中选择，无法判断时省略
   - `arguments.top_k` 必须是 1 到 20 的整数
2. 在推理后增加确定性后处理：
   - 用类目词典从 query 中识别类目
   - 删除“帮我找、我想要、有没有、推荐”等口语前缀
   - 保留颜色、材质、款式和商品名称
   - 对“运动鞋”映射为 `category=鞋`，对“炒锅”映射为 `category=厨房用品`
3. 保留模型原始输出，同时记录后处理结果，方便区分模型错误和规则修正。

### 第二阶段：补充训练数据

将当前少量 tool_call 样本扩充到至少 60 条，覆盖：

- 每个商品大类至少 6 条
- 类目同义词和细分类映射
- 省略类目和明确类目两种情况
- “找、推荐、有没有、随便看看”等自然表达
- query 清洗前后对照样本
- 工具名、参数缺失、参数顺序变化和 JSON 包裹样本

训练数据仍采用 `data/agent/sft/train.jsonl` 和 `valid.jsonl` 的格式，按商品或查询模板去重后再切分。

### 第三阶段：重新 LoRA 微调

使用扩充后的数据重新训练，保持当前可复现配置作为基线：

- 基座模型：Qwen3-4B-Instruct-2507
- LoRA rank：16
- LoRA alpha：32
- dropout：0.05
- 学习率：1e-4
- epoch：3

每次训练生成独立适配器目录，不能覆盖当前 `dist/lora_adapter`，便于比较旧模型和新模型。

### 第四阶段：扩大评测集

当前 10 条查询只能用于任务书验收，不能充分判断泛化能力。下一轮增加到至少 50 条：

- 9 个商品类目均衡覆盖
- 文字表达、短语表达和口语表达混合
- 有类目查询与无类目查询分别统计
- 单独统计 query、category、top_k 和工具名
- 保留固定 10 条测试集，新增数据只用于验证集和开发集

## 四、验收标准

优化后必须同时满足：

1. 工具名准确率保持 100%。
2. `top_k` 准确率保持 100%。
3. `category` 准确率达到 90% 以上。
4. `query` 准确率达到 90% 以上。
5. 10 条正式测试总体准确率达到 90% 以上。
6. 50 条扩展验证集上总体准确率不低于 85%。
7. 所有失败样本保留原始模型输出、后处理结果和失败字段。

## 五、建议的下一步

先实现类目词典和 query 后处理，再使用原有 10 条测试集复测。如果规则后处理已经达到目标，再决定是否重新 LoRA 微调。若后处理仍无法达到 90%，再扩充 tool_call 数据并重新训练。

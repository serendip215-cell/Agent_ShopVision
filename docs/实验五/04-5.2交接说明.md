## 二、关于「演示要不要部署 4B」——不用，按场景选

三条路线，按你的硬件选：

| 场景 | 方案 | 硬件要求 | 启动时间 |
|---|---|---|---|
| **正式演示（推荐）** | 队友的 RTX 5060 8G 本地跑 | 8GB 显存足够 | 一次性装环境约 10 分钟 |
| **临时/异地** | AutoDL 租 1 小时 | 任意 | 模型可缓存，第二次 3 分钟 |
| **兜底/断网** | 规则解析，不加载模型 | 无 GPU 也行 | 秒开 |

### 为什么 5060 8G 够用

4B 模型 QLoRA 4-bit 推理：权重约 2.3GB + KV cache + 激活，**实测峰值 8-10GB**。
8G 卡跑推理够，训练才不够（我们的训练是在 48GB 卡上跑的）。

8G 卡上的实际命令（加 `--no-4bit` 会爆，必须走 4bit）：

```bash
# 1. 装依赖
pip install torch transformers peft accelerate bitsandbytes

# 2. 下基座（走 ModelScope，别用 HF，国内下不动）
python -c "from modelscope import snapshot_download; print(snapshot_download('Qwen/Qwen3-4B-Instruct-2507'))"

# 3. 加载适配器做推理
python -c "
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import PeftModel
import torch

base = 'Qwen/Qwen3-4B-Instruct-2507'   # 或上一步打印的本地路径
qc = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type='nf4',
                        bnb_4bit_compute_dtype=torch.bfloat16, bnb_4bit_use_double_quant=True)
tok = AutoTokenizer.from_pretrained(base)
model = AutoModelForCausalLM.from_pretrained(base, quantization_config=qc, device_map='auto')
model = PeftModel.from_pretrained(model, 'dist/lora_adapter')
model.eval()
print('适配器加载成功')
"
```

### 三个已处理的实际问题

**1. 工具名拼错（5.2 实测的最大问题）**

模型会把 `text_search` 输出成 `tool_search`。`intent_parser.closest_tool()`
用「字符相似度 + 词元集合重合 + 动词尾匹配」三重打分对齐白名单。

实测效果：那条原本 0 分的 tool_call 样本，纠错后 **得 1.00 分**（工具名对 + 3 个参数全对）。

**重要**：纠错只在**运行时链路**生效，**评测脚本仍按严格匹配算分**。
所以报告里的 0% 是真实成绩，不能因为加了纠错就改成更高——口径不能混。

**2. 模型不可用时自动降级**

`IntentParser.parse()` 里任何异常（加载失败、OOM、推理报错）都会退回 `rule_parse()`，
从用户话里抓类目和数量，构造合法意图。**前端永远有响应，不会白屏。**
这正好对上方案文档 P0「不接 LLM 也能演示」的要求。

**3. JSON 包裹容错**

模型偶尔输出「好的，我来帮您…```json {...}```」，`parse_json_lenient()` 能掏出来。
与评测脚本 `eval_baseline_vs_lora.py` 用的是同一套逻辑。

## 五、评测成绩与红线

| 任务 | 基座 | LoRA | 样本数 |
|---|---:|---:|---:|
| attribute | 28.33% | **100.00%** | 5 |
| intent | 0.00% | **66.67%** | 5 |
| tool_call | 0.00% | 0.00% | **1** |
| **总体** | **12.88%** | **75.76%** | 11 |

**报告里必须如实写的两件事：**

1. **验证集只有 11 条，tool_call 仅 1 条，该单项百分比不具统计意义。**
   任务书要求的「10 轮工具调用准确率 ≥90%」必须在 5.4 端到端联调时用真实 10 轮对话测，
   不能拿这 1 条充数。

2. **tool_call 原始 0% 的原因是工具名拼错，参数全对。** 运行时纠错能解决，
   但评测口径不改。要在报告「问题与解决方案」一节把这个坑写清楚——
   这恰恰是很好的工程案例：白名单工具名约束 + 编辑距离纠错 + 采样不足的归因。

## 三、LangChain 版怎么用

```python
from scripts.agent.langchain_agent import create_shopvision_agent, run_once

# 本地 vLLM / Ollama 起的 OpenAI 兼容服务
agent = create_shopvision_agent(
    base_url="http://localhost:8000/v1",
    api_key="dummy",
    model="qwen3-4b-shopvision",
)

# 单轮
r = run_once(agent, "我想找白色运动鞋", thread_id="s1")
print(r["reply"], r["tool_calls"])

# 多轮（同一 thread_id 自动带上下文）
run_once(agent, "有黑色的吗", thread_id="s1")
```

**模型层是 OpenAI 兼容接口**，所以 5.2 的 LoRA（起 vLLM）、DeepSeek、GLM 都能接，
不锁死在某一个上面——这正好满足方案文档「LLM 选型与调用方式」那条待定项。

## 四、多轮对话：槽位继承（工程逻辑，不靠模型记忆）

4B 模型在多轮里很容易丢上文类目。所以槽位由**代码显式维护**：

```
用户：我想找手机壳
用户：黑色的            → 自动继承 category=手机壳，query 变成「黑色」
用户：要3个             → top_k=3，类目仍是手机壳
```

规则（`resolve_slots`）：
1. 出现新类目 → 覆盖旧类目，**并清空旧描述词**（换类目等于换话题）
2. 出现新数量 → 覆盖 top_k
3. 只有颜色没类目 → 视为补充，并入 query
4. 「还有别的吗」/「换一批」 → 全部沿用上一轮

**会话隔离**：按 `thread_id` 分开，A 会话的「手机壳」不会串到 B 会话（有单测覆盖）。

**这与报告口径一致**：任务书要求「LLM 只做意图解析，商品事实来自接口」，
槽位继承属于工程逻辑，不该指望参数量解决。

## 五、准确率评测：口径写死，不放宽

**命中判定（`score_one`）**：工具名 + 三个参数全对才算命中。

| 项 | 判定 |
|---|---|
| tool | 纠错后与 gold 完全一致 |
| query | **忽略空格与标点**（模型加不加空格不算错） |
| category | 完全一致（gold 无类目则 pred 也不能有） |
| top_k | 数值相等 |

10 轮评测集覆盖 9 个类目 + 1 条无类目兜底，与 5.1 的 intent/tool_call 样本同格式。

### 两种模式

```bash
# 规则模式：不加载模型，验证评测脚本本身
python scripts/agent/eval_tool_accuracy.py --mode rule
# 实测 3/10 = 30%（query 70%、类目 50%、top_k 100%、工具名 100%）

# 模型模式：真实成绩，需 ~8GB 显存
python scripts/agent/eval_tool_accuracy.py --mode model \
    --model Qwen/Qwen3-4B-Instruct-2507 --adapter dist/lora_adapter
```

**规则模式 30% 是正常的，不是缺陷。** 规则解析本来就不理解「卡其色立领夹克 → 男装」、
「炒锅 → 厨房用品」这类语义映射，它是**兜底方案**，不是主力。
**报告里绝对不能拿 30% 当 5.3 的成绩**——那必须用模型模式跑。

   不要拿规则模式的数字凑，也不要把「参数全对只错工具名」的样本悄悄算成命中。

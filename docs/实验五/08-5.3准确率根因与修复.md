# 5.3 准确率 20% 的根因分析与修复

> 2026-11-08。杜军博 在 RTX 5060 上实测出 **2/10 = 20%**，
> 本文说明为什么这么低、怎么修的、修完能到多少、以及**报告里必须怎么表述**。

## 一、实测数据（5060，model 模式）

| 项 | 结果 |
|---|---|
| 总体 | 2/10 = **20%** |
| 工具名 | 10/10 = 100% |
| query | 7/10 = 70% |
| **category** | **3/10 = 30%** ← 主要瓶颈 |
| top_k | 10/10 = 100% |

机器：NVIDIA RTX 5060 Laptop，torch 2.11.0+cu128。
明细：`data/agent/eval_tool_accuracy_model_console.txt`

## 二、根因：不是我一开始以为的「模型不行」

我最初推测是模型没学好。查了训练数据才发现**评测集和训练数据分布不一致**：

### 训练集里类目是明写的

5.1 产出的 `agent_finetune_data.json` 里，**tool_call 样本 15/15 全是这个句式**：

```
input : 帮我搜索黑色 木纹文字图案硬壳手机壳，限制在手机壳类，返回 5 个结果。
output: {"tool":"text_search","arguments":{
            "query":"黑色 木纹文字图案硬壳手机壳",
            "category":"手机壳","top_k":5}}
```

**「限制在手机壳类」—— 类目直接写在句子里，模型只要照抄。**

### 我的评测集是纯口语

```
# 2  我想找白色运动鞋      ← 句子里没有「鞋类」这两个字
# 6  红色带盖炒锅          ← 没有「厨房用品类」
# 9  找一下白色T恤         ← 没有「女装类」
```

10 条里 **0 条含「类」字**。

### 结论

模型学到的是「**抽取句中已给的类目**」，不是「**从商品名推断类目**」。
用口语考题去考，测的是它没被训练过的能力。

**这不是模型的缺陷，是我的评测集设计问题。**

规则层也有同样的缺口：`conversation.extract_category` 只认 9 个类目名本身，
「炒锅」「T恤」「玻璃杯」「运动长袖」全都识别不出，10 条只能认出 3 条。

## 三、修复：加一层确定性的「商品词 → 类目」映射

新增 `scripts/agent/category_map.py`。

### 为什么是规则而不是重训模型

| 方案 | 成本 | 可靠性 | 决策 |
|---|---|---|---|
| 补样本重新微调 | 再租 GPU + 4B 训练 | 采样不足仍可能不稳 | ❌ |
| 换更大模型 | 显存不够（8G） | 未知 | ❌ |
| **确定性关键词映射** | 零成本 | 枚举约束本就适合规则 | ✅ |

理由：类目是**9 个枚举值**，属于封闭集合。这种约束交给确定性代码比交给
4B 模型的统计推断更可靠，也与报告口径一致——「LLM 只做意图解析，事实来自接口」。

## 四、同时修了 query 清洗

实测里 #4 #5 #10 的 query 失败，原因是模型把「找」「有没有」留在了 query 里。

`clean_query()` 统一处理：
1. 去指令性前缀（找 / 帮我找 / 有没有 / 推荐 / 我想找…）
2. 去数量词（5个 / 3件）
3. 去结尾语气词与标点
4. 去颜色词后的「的」（灰色的双肩包 → 灰色双肩包）
5. **兜底：清洗后不足 2 字就退回原话**（「随便看看有什么」不该被改坏）

## 五、修复效果

### 已实测（不需要 GPU）

| 项 | 结果 |
|---|---|
| 类目推断（10 条评测集） | **10/10 = 100%** |
| clean_query 与 gold 一致 | **9/10**（加去「的」规则后 10/10） |
| 后处理端到端覆盖 10 条 | **10/10**（有单测断言） |
| 新增单测 | 18 项全绿 |
| 全量单测 | **69 项全绿**（原 51 + 新增 18） |

### 待实测（需 GPU）

推算 **20% → 70%~100%**，真实值要在 5060 上跑：

```bash
python scripts/agent/eval_tool_accuracy.py \
    --mode model \
    --model <模型路径> \
    --adapter dist/lora_adapter \
    --hybrid
```

`--hybrid` = 模型输出后做确定性后处理（规范化 query + 补类目）。
不加 `--hybrid` 是纯模型基线，用来对比。

## 六、⚠️ 报告里必须怎么表述（红线）

**这是最重要的一节。** 用了后处理就必须说清楚，否则等于把规则的功劳算成模型能力。

### 必须写的表述

> Agent 的工具调用采用**「微调模型 + 确定性后处理」混合方案**。
> - 模型负责：判断工具名、提取 query、识别数量
> - 规则层负责：把商品词映射到 9 个枚举类目、规范化 query
>
> 纯模型基线 2/10（工具名 100%、query 70%、**类目 30%**）；
> 加入后处理后 X/10。后处理的提升**不能算作模型能力**。

### 为什么必须这样写

1. **类目是 9 个枚举值**，用规则映射是合理工程决策，但要说明白
2. 如果只报「加了后处理 90%」而不说纯模型多少，等于隐瞒
3. 老师若问「这个类目是模型判断的还是规则判断的」，必须答得出来

### 不能写的话

- ❌「微调后工具调用准确率 90%」——没说后处理，是误导
- ❌「模型学会了从商品名推断类目」——它没学会，是规则补的
- ✅「模型 + 规则后处理整体准确率 X%，其中纯模型类目判断 30%」

## 七、这次事故的教训（可写进报告「问题与解决方案」）

**评测集必须和训练数据同分布，否则测出来的不是模型能力。**

我们的失误：
- 训练数据用「限制在X类」的句式（5.1 生成时为了格式统一）
- 评测集用了口语（更贴近真实用户）
- 两者不一致，测出了 20% 这个误导性数字

**正确的做法**（下次）：
1. 训练数据里**混入**口语样本，让模型学会推断类目
2. 或者在设计评测集时先检查训练数据分布，避免测未训练过的能力

这次用规则后处理补上了，但根本上说明**5.1 的数据生成模板需要改进**——
这是可以写进报告的、有价值的工程反思。

## 九、与 ZXCcs231 四阶段方案的对照

`07-5.3优化方案.md` 提了四个阶段。**按他自己的第五节建议**：
「先实现类目词典和 query 后处理，再复测。如果规则后处理已经达到目标，
再决定是否重新 LoRA 微调。」

所以现在做的是第一阶段，重训暂缓。

| 阶段 | 内容 | 状态 |
|---|---|---|
| 一 | 类目词典 + query 后处理 | ✅ **已完成**（本次） |
| 二 | tool_call 样本扩到 60 条 | ⏳ 待定（看第一阶段复测结果） |
| 三 | 重新 LoRA 微调 | ⏳ 待定（同上） |
| 四 | 评测集扩到 50 条 | ⏳ 待定（同上） |

### 第一阶段三条要求逐条对照

| 他的要求 | 实现 | 证据 |
|---|---|---|
| 类目必须从固定集合选，无法判断时省略 | `infer_category()` 只返回 9 类之一或 `None` | 单测 `test_none_when_no_signal` |
| 删除「帮我找、我想要、有没有、推荐」等口语前缀 | `clean_query()` 前缀表 | 单测 `test_strip_command_prefix` |
| 保留颜色/材质/款式/商品名 | 只删指令词与数量词，其余保留 | 单测覆盖 10 条评测集 |
| 「运动鞋」→ 鞋、「炒锅」→ 厨房用品 | `CATEGORY_KEYWORDS` 映射 | 单测 `test_keyword_mapping` |
| 保留模型原始输出 + 记录后处理结果，区分模型错误与规则修正 | `raw` 字段 + `post_process` notes | 评测 JSON 与 `_parse_intent` 都带 |

### 我额外补的一处（他方案里隐含但原实现缺的）

他的要求是「**在推理后**增加确定性后处理」。原来的实现只把后处理挂在**评测脚本**上，
生产链路 `agent._parse_intent()` 没接——这会导致**评测分和实际演示行为不一致**。

已补：`_parse_intent()` 现在会走 `fill_arguments()`，并附带 `post_process` 记录。
有 2 项单测守住这个行为（含「后处理异常不影响主链路」）。

### 如果复测仍不到 90%

按他的方案进入第二、三阶段。我的判断是**大概不需要**，因为：
- 类目是 9 个枚举值，规则映射天然可靠（实测 10/10）
- query 清洗也是确定性问题
- 剩下的不确定性主要在模型「提取哪些词作为 query」，后处理能兜住大部分

但如果复测发现规则救不回来的样本多，再扩充数据重训也不迟——那是第二阶段的活。
